# Phase 0 — Research & Design Decisions: Execution Events, Exceptions, SLA Risk, and In-App Alerts

**Feature**: 007-execution-events-exceptions · **Date**: 2026-05-31 · **Spec**: [spec.md](./spec.md)

This slice has **no open NEEDS CLARIFICATION** — the three `/speckit-clarify` sessions (2026-05-31, -31b, -31c) resolved every decision that changes data model, scope, or tests: the SLA trigger→state map (window-miss ⇒ *Late*; everything else ⇒ *At Risk*; *Breached* unreachable in MVP), worst-state-wins multi-trigger precedence, acknowledged-alert suppression with `active OR acknowledged` uniqueness, `sla_status` kept as `text` + a new `sla_reasons text[]` (no new enum), and Loading/Unloading recordable via `status_change` (no new `trip_event_type` member). The remaining open items are gated business inputs (§29 Input #2 per-customer SLA rules, per-milestone planned times) and later-slice dependencies (the two §17 document/billing alert cases) — all scaffolded as documented defaults, never invented (Constitution II). The decisions below pin the technical approach against the **actual current codebase** (001 auth/audit/i18n, 002 master data, 003 trip domain/service/append-only `trip_events`/status machine, 005 read models + UI shell, 006 assignment/confirmation state, and the 004-built worker + pg-boss queue).

---

## R0 — Reuse vs build: what 007 adds

**Decision**: 007 introduces **four new tables** (`exceptions`, `reason_codes`, `customer_sla_rules`, `alerts`), **three new Postgres enums** (`exception_status`, `exception_severity`, `exception_responsible_party` — the 5-value set), **two new pure domain modules** in `@brazil-tms/shared` (`domain/sla-risk.ts` SLA evaluator + policy, `domain/exceptions.ts` lifecycle + severity/responsible-party/category vocab), **new Zod schema files** (`schemas/exception.ts`, `schemas/customer-sla-rule.ts`, `schemas/trip-event.ts`/milestone, `schemas/alert.ts`), **new service functions** + **read-model extensions** in `@brazil-tms/db`, **ALTER** of `trips` (compute `sla_status` + add `sla_reasons text[]`) and `trip_events` (wire the `exception_id` FK), the **first activation of a scheduled worker job** on the existing pg-boss queue, **~12 BFF endpoints**, and the UI fills (interactive timeline, exception panel, Exception Management screen, SLA indicator/"At risk" view, alerts surface, dashboard widgets, customer-SLA-rule admin). It adds **no new permission key**, **no new package**, **no new worker process**, and **no `sla_status` enum** (D4) and **no `trip_event_type` member for Loading/Unloading** (D5). `alert_state` and `reason_codes.category` are **CHECK-constrained text**, not enums (R0 rationale below).

**Rationale**: EVT/EXC/SLA-001..004 + the PRD §14.1 Exception / Reason Code / Customer SLA Rule entities + the §17 alert cases are exactly slice 007's ownership (`docs/SPEC-SLICING.md`). Everything else — trip model, status machine, `transitionTripStatus`, `trip_events` append-only log, master data, the 006 assignment/confirmed-at state, the 005 board/detail/dashboard read models, polling, i18n, the worker package + pg-boss queue — already exists and is reused read-only or extended in place (Constitution I DRY/YAGNI, III single source of record). Three enums are created (vs CHECK text) because exception status/severity/responsible-party are **hard fixed domain sets** referenced by service logic and the evaluator (the codebase convention is `pgEnum` for fixed sets, `text + CHECK` for business-mutable value sets — `enums.ts` vs `cancellation_options.kind`). `alert_state` is the borderline case but stays **CHECK text** to mirror nothing in `enums.ts` would be referenced by Drizzle column types the way the evaluator references severity — and to keep the partial-unique predicate (`state IN ('active','acknowledged')`) readable; **`alert_case` is also CHECK text** (it enumerates all 8 §17 cases including the 2 deferred, so the set evolves with 008/009 — text + CHECK avoids a `CREATE TYPE` migration when those land).

**Alternatives rejected**: a `configure_sla` permission key (the matrix has none; spec clarification reuses `manage_commercial_data`); an `sla_status` enum (D4 — kept `text` + CHECK so 003's existing column type is unchanged); a new `trip_event_type` value for Loading/Unloading (D5 — they are `status_change` transitions); making `alert_case`/`alert_state` enums (a `CREATE TYPE` migration to add the deferred document/billing cases is avoidable churn — CHECK text per the `cancellation_options` precedent).

## R1 — `exceptions` table shape (PRD §14.1, EXC-002)

**Decision**: New table `exceptions` (snake_case): `id` (uuid PK), `trip_id` (FK→trips, not null), `reason_code_id` (FK→reason_codes, not null), `severity` (`exception_severity` enum, not null), `status` (`exception_status` enum, not null default `'open'`), `responsible_party` (`exception_responsible_party` enum, not null), `owner_user_id` (FK→users, **not null** — defaults to creator, reassignable), `description` (text, not null), `opened_at` (timestamptz not null default now), `resolved_at` (timestamptz, nullable), `closure_notes` (text, nullable), `created_by_user_id` (FK→users, not null), `created_at`/`updated_at` (timestamptz not null default now). **Category is derived, NOT stored** — it is read from the linked `reason_codes.category`. Attachments are **deferred to 008** (no column added now). Full DDL in [data-model.md](./data-model.md).

**Rationale**: 1:1 with PRD §14.1's enumerated Exception fields plus the spec's `owner` addition (FR-008 — required internal-user ref, defaults to creator, reassignable). **Category stored-vs-derived → derived**: EXC-004's category lives on the `reason_codes` row (FR-010), and the spec ("category derived from reason_code") plus Constitution III (single source) make a stored copy a drift hazard; the Exception Management category filter joins through `reason_code_id`. `responsible_party`/`severity` are **not null** (every exception has both — reason-code defaults pre-fill but the stored value is explicit). FKs use inline `.references(() => x.id)` with default `ON DELETE no action` (matches `trips`/`drivers`). Indexes for the EXC-013 Exception Management filters: `exceptions_trip_idx (trip_id)`, `exceptions_status_idx (status)`, `exceptions_severity_idx (severity)`, `exceptions_owner_idx (owner_user_id)`, `exceptions_reason_idx (reason_code_id)`, `exceptions_opened_idx (opened_at desc)` (age filter).

**Alternatives rejected**: storing `category` denormalized on `exceptions` (drift vs `reason_codes`; rejected per spec); an `attachments jsonb` column now (storage surface is 008 — YAGNI, deferred without blocking the lifecycle per Assumption 7); REVOKE-hardening `exceptions` (it mutates — status, owner, closure — like `trip_assignments`, not append-only; see R15).

## R2 — `reason_codes` table shape (PRD §14.1, EXC-004)

**Decision**: New config table `reason_codes` mirroring 003's `cancellation_options` convention: `id` (uuid PK), `code` (text not null, unique), `category` (**text + CHECK** to the EXC-004 12-value set: `delay, no_show, breakdown, driver_issue, customer_delay, loading_delay, unloading_delay, documentation, accident, route_deviation, cancellation, other`), `label_pt` (text not null, pt-BR display), `default_severity` (`exception_severity` enum, not null), `default_responsible_party` (`exception_responsible_party` enum, not null), `active` (boolean not null default true), `sort_order` (integer not null default 0), `created_at`/`updated_at`. Seeded as **labeled scaffolding** (Constitution II): one default row per EXC-004 category with a sensible `default_severity`/`default_responsible_party` — explicitly NOT final business sign-off (mirrors 003's `cancellation_options` gap, Blocked-item #5).

**Rationale**: matches the `cancellation_options` enum-vs-config rule exactly — reason codes are a **business-mutable** value set, so `text + CHECK` for `category` and config rows, not a `pgEnum` (the category set is fixed in MVP but the *codes* are config rows administered later). `default_severity`/`default_responsible_party` ARE enums (they reference the fixed exception scales). Reason codes are **one configurable set, not per-customer code** (Constitution V). Unlike `cancellation_options` (which seeds zero `reason` rows and fails closed), 007 seeds the EXC-004 categories so the Exception flow is demonstrable end-to-end at MVP; the seed is labeled scaffolding pending sign-off.

**Alternatives rejected**: a `reason_code_category` enum (the 12 categories are stable but the convention reserves enums for sets referenced by domain logic across the codebase — category is filter/display metadata, so CHECK text is the lighter fit and matches `cancellation_options.kind`); reusing `cancellation_options` with a third `kind` (semantically distinct — exceptions ≠ cancellations; the spec explicitly says "Distinct from 003's `cancellation_options`").

## R3 — `customer_sla_rules` table + single-applicable-rule precedence (PRD §14.1, CUST-005)

**Decision**: New table `customer_sla_rules`: `id` (uuid PK), `customer_id` (FK→customers, not null), `lane_id` (FK→lanes, nullable scope), `vehicle_type` (`vehicle_type` enum, nullable scope), `pickup_tolerance_minutes` (integer, not null), `delivery_tolerance_minutes` (integer, not null), `confirmation_cutoff_minutes` (integer, not null — lead time before pickup), `at_risk_warning_minutes` (integer, not null — warning window), `effective_start` (timestamptz, nullable), `effective_end` (timestamptz, nullable), `active` (boolean not null default true), `created_at`/`updated_at`. **Single-applicable-rule precedence is resolved in the evaluator's query**, NOT a DB constraint: `WHERE customer_id = ? AND active AND (effective window covers the trip's pickup) AND (lane_id = trip.lane_id OR lane_id IS NULL) AND (vehicle_type = trip.planned_vehicle_type OR vehicle_type IS NULL)` `ORDER BY (lane_id IS NOT NULL) DESC, (vehicle_type IS NOT NULL) DESC, effective_start DESC NULLS LAST LIMIT 1`. **Absence of any matching row ⇒ company defaults + that customer reported SLA sign-off blocked** (FR-022). Indexes: `customer_sla_rules_customer_idx (customer_id)`, `customer_sla_rules_scope_idx (customer_id, lane_id, vehicle_type)`.

**Rationale**: precedence **lane > vehicle-type > customer-default, tie-break latest `effective_start`** is exactly the spec edge case ("overlap resolves to the most specific in-scope, currently-effective rule"). It lives in the evaluator's `ORDER BY ... LIMIT 1`, **NOT** a Postgres exclusion constraint — the rule set is gated, low-volume, human-administered business data; an exclusion/btree_gist constraint is YAGNI (Constitution) and would reject legitimate overlapping scopes that the precedence already disambiguates. Tolerances/cutoffs are stored as **minutes (integer)** for unambiguous Luxon arithmetic in UTC. This is **per-customer commercial config** → administered via the reused `manage_commercial_data` key (R12), not a new `configure_sla` key.

**Alternatives rejected**: a DB exclusion constraint preventing overlapping rules (YAGNI — precedence in the query handles overlap; gated low-volume data); separate `pickup_rule`/`delivery_rule` jsonb blobs (opaque, un-queryable, harder to validate — explicit minute columns are clearer and Zod-checkable); storing on-time "definition" as free text (the MVP definition is window ± tolerance; a tolerance integer captures it).

## R4 — `alerts` table shape + idempotency (PRD §17, FR-023/024)

**Decision**: New table `alerts`: `id` (uuid PK), `trip_id` (FK→trips, not null), `alert_case` (**text + CHECK** to all 8 §17 cases: `unassigned_within_window, unconfirmed_within_window, missed_origin_arrival, missed_departure, missed_destination_arrival, high_severity_exception, completed_missing_documents, billing_blocked_missing_proof`), `severity` (`exception_severity` enum, not null — reuse the same scale), `state` (text + CHECK `in ('active','acknowledged','resolved')`, not null default `'active'`), `created_at` (timestamptz not null default now), `acknowledged_by_user_id` (FK→users, nullable), `acknowledged_at` (timestamptz, nullable), `auto_resolved_at` (timestamptz, nullable), `updated_at`. **Partial unique index** `alerts_trip_case_open_uq ON (trip_id, alert_case) WHERE state IN ('active','acknowledged')` enforces D3 uniqueness. Idempotent generation = `INSERT ... ON CONFLICT (the partial-unique target) DO NOTHING`. Auto-resolution = `UPDATE alerts SET state='resolved', auto_resolved_at=now() WHERE trip_id=? AND alert_case=? AND state IN ('active','acknowledged')` when the condition clears. Indexes: `alerts_trip_idx (trip_id)`, `alerts_state_idx (state)`.

**Rationale**: directly encodes D3 (Clarifications 2026-05-31c) — uniqueness scope is **`active OR acknowledged`** (not active alone), so a dismissed-but-still-true alert is not re-spammed and the worker auto-resolves it once the condition clears; a later recurrence inserts a fresh row (the prior row is `resolved`, outside the partial-unique predicate). `ON CONFLICT DO NOTHING` against the partial-unique target makes both the synchronous BFF path (R11) and the worker sweep (R10) safe to run concurrently (FR-024 idempotency). `alert_case` is **text + CHECK** including the two deferred cases (`completed_missing_documents`, `billing_blocked_missing_proof`) so 008/009 wire them with no `CREATE TYPE` migration (R0); 007 generates only the six in-scope cases (FR-026). `severity` reuses `exception_severity` (no separate alert-severity scale — KISS). `alerts` is **mutable** (acknowledge/resolve) → no REVOKE (R15).

**Alternatives rejected**: deriving alerts on the fly (the spec clarified **stored** so they list/count/acknowledge and don't re-spam); a unique constraint on `(trip_id, alert_case)` all-time (would block legitimate recurrence after clear — D3 requires re-fire); an `alert_case`/`alert_state` enum (CHECK text avoids a `CREATE TYPE` migration when 008/009 add cases, and matches the `cancellation_options` precedent).

## R5 — `trips` ALTER: compute `sla_status`, add `sla_reasons text[]` (D4, FR-014)

**Decision**: Keep `trips.sla_status` as **`text`** (003's existing nullable placeholder column type — unchanged) and add a CHECK constraint `trips_sla_status_ck CHECK (sla_status IS NULL OR sla_status IN ('on_track','at_risk','late','breached'))`. Add a new sibling column `sla_reasons text[]` (nullable, the first array column in the schema). Both are written **atomically** by the evaluator-applying service in the same `tx.update(trips).set({ slaStatus, slaReasons, updatedAt })`. **No `sla_status` enum** (D4). Drizzle helper: `text("sla_reasons").array()`; verify `drizzle-kit` emits `text[]` and apply the array-expansion gotcha (MEMORY `drizzle_sql_array_expansion`: use `IN ${ids}` tuple form, never `= ANY(${arr}::uuid[])`) when querying it.

**Rationale**: D4 (Clarifications 2026-05-31c) — `sla_status` stays `text` validated to the four values via Zod + CHECK (no new enum; reasons are a small fixed set always read alongside the status, never queried independently, so an array column beats a join table per YAGNI). `sla_reasons text[]` is the **first** `.array()` column in `packages/db` (RECON confirms none exist) — must verify the generated `0006` migration emits `text[]` correctly. Atomic write keeps status and reasons consistent on every recompute (FR-014).

**Alternatives rejected**: an `sla_status` enum (D4 forbids — 003's column is `text`); a separate `trip_sla_reasons` child table (over-engineered — reasons are read-only-alongside metadata, YAGNI); a `jsonb` reasons blob (a `text[]` of fixed reason codes is queryable and CHECK-able; jsonb is opaque).

## R6 — `trip_events` usage: wire `exception_id` FK, no new event-type member (D5, FR-003/004)

**Decision**: ALTER `trip_events` to add the FK on the existing `exception_id` column → `exceptions(id)` (`ON DELETE no action`; drizzle-kit emits this once the schema `.references()` is added, but the cross-feature FK activation is hand-verified). **Do NOT add a `trip_event_type` member for Loading/Unloading** (D5) — they are recorded as `status_change` events (new_status = `loading`/`unloading`). **DO add `trip_event_type` member `note`** for EVT-003 free-form events (currently every insert is `status_change`; a free-form note is not a status change and needs a distinct type so the timeline can render and filter it). **Do NOT add `gps`/`driver_input` to `trip_event_source`** (003's comment reserves them, but 007 has no GPS/driver-input feature — out of scope §20.2; YAGNI). Manual milestone/note events use `source='operator_manual'`. `trip_events` stays **append-only** (keeps its REVOKE UPDATE/DELETE; insert+select only).

**Rationale**: D5 (Clarifications 2026-05-31c) — Loading/Unloading add **no** event-type member. The **single** vocabulary extension is `note` (the minimal-and-justified decision from R0): free-form events (FR-004, EVT-003) are not status changes, so they cannot be `status_change`, and there is no fitting existing member (`origin_arrived`/`loaded`/etc. are milestone-specific). `gps`/`driver_input` sources are explicitly out of scope (manual updates only, §20.2 EVT-006/007 deferred) — adding them now is speculative (YAGNI). The `exception_id` FK is the forward hook 003 left for 007 to wire (003 data-model §Relationships). Append-only preserved (Constitution III).

**Alternatives rejected**: an `exception_logged` event type (an exception is its own `exceptions` row + optional linked event via `exception_id` — a dedicated event-type member is redundant; the linked note/`status_change` event carries `exception_id`); adding `gps`/`driver_input` now (no consumer in 007 — YAGNI); reusing `status_change` for notes (a note has no status before/after — would corrupt timeline semantics).

## R7 — SLA evaluator: pure module in `shared` with `DEFAULT_SLA_POLICY` (FR-014..019)

**Decision**: A pure, DB-free module `packages/shared/src/domain/sla-risk.ts` exporting `evaluateSlaRisk(ctx, rule): { status: SlaStatus; reasons: SlaReason[] }`. `SLA_STATUSES = ['on_track','at_risk','late','breached'] as const` (type `SlaStatus`; severity order index = `on_track(0) < at_risk(1) < late(2) < breached(3)`). `SLA_REASONS = ['missing_assignment','missed_confirmation','delayed_origin_arrival','delayed_loading','delayed_departure','delayed_destination_arrival','open_high_severity_exception'] as const` (type `SlaReason`). The evaluator encodes the **D1 trigger→state map**: `delayed_origin_arrival`/`delayed_destination_arrival` (missed planned arrival window) ⇒ **Late**; `missing_assignment`/`missed_confirmation`/`delayed_loading`/`delayed_departure`/`open_high_severity_exception` ⇒ **At Risk**; none ⇒ **On Track**. **Worst-state-wins** (D2): `status` = max-severity of all fired reasons' states; `reasons` retains **all** fired triggers. **Breached is never produced in MVP** (the value exists but no MVP trigger maps to it — needs a customer threshold, §29 Input #2). `ctx` carries `now`, the trip's planned pickup/delivery windows + `currentStatus` + `confirmedAt` + `assignmentPresent` + `openHighSeverityExceptionCount` + `currentStatusEnteredAt` (for time-in-status). **No-planned-window branch**: when a window is absent, skip the window-based risk for that leg but still evaluate assignment/confirmation/exception (FR-016 falls back to defaults but the *window itself* may be null). `DEFAULT_SLA_POLICY` config object with explicit, labeled-configurable default magnitudes: **at-risk warning window = 60 min**, **on-time pickup/delivery tolerance = 0 min** (window edge is the cutoff), **confirmation cutoff lead time = 120 min before pickup**, **time-in-status threshold (loading/departure) = 120 min**. Terminal/cancelled trips short-circuit to no evaluation (Edge Case).

**Rationale**: STACK §3.13 names the SLA evaluator a required Vitest focus — a pure function is unit-testable without a DB (mirrors 006's `assignment-eligibility.ts`). Authority is server-side (Constitution III / STACK §6); the BFF and worker both call it, the UI never computes (FR-014). Concrete default magnitudes make SC-005/SC-006 testable now (Constitution II — labeled configurable, not invented; `DEFAULT_SLA_POLICY` is the seam a `customer_sla_rules` row overrides). Time-in-status (FR-018) reads `currentStatusEnteredAt` (the latest `status_change` event timestamp for the current status) since per-milestone planned times are unavailable (§29 Input #2); the recordable Loading/Unloading sub-states (D5/FR-001) make `delayed_loading` measurable. The barrel adds `export * from "./domain/sla-risk"` after `assignment-eligibility` (RECON: that is the established slot).

**Alternatives rejected**: computing risk in SQL/views (un-unit-testable, violates the pure-evaluator quality gate); computing in the BFF route handlers (duplicated between BFF and worker — DRY); a single magic threshold (the spec distinguishes warning-window vs cutoff vs time-in-status — separate labeled defaults).

## R8 — Exception lifecycle: transition helper in `shared` + services mirroring 003 pattern (FR-009)

**Decision**: A pure `packages/shared/src/domain/exceptions.ts` exporting `EXCEPTION_STATUSES = ['open','monitoring','resolved','cancelled'] as const`, `EXCEPTION_SEVERITIES = ['low','medium','high'] as const` (**`high` is the SLA/alert trigger**), `EXCEPTION_RESPONSIBLE_PARTIES = ['customer_caused','brazil_transports_caused','carrier_caused','force_majeure','unknown'] as const` (the **5-value** set adding `force_majeure` — distinct from 003's 4-value `cancellation_responsible_party`), the EXC-004 `REASON_CODE_CATEGORIES` const, and `canTransitionException(from, to): boolean` over the legal map: **`open↔monitoring`**; `open→resolved`, `open→cancelled`, `monitoring→resolved`, `monitoring→cancelled`; **`resolved`/`cancelled` terminal** (no reopen). Service functions in `packages/db/src/trips/exceptions.ts` — `createException`, `updateException` (owner reassign / severity / responsible-party / description edits), `transitionException` (Open/Monitoring/Resolved/Cancelled, requires `closure_notes` + sets `resolved_at` on Resolved) — mirror the **003 transaction+audit pattern** exactly: pre-tx legality (`canTransitionException`) outside the tx; inside one `db.transaction`, guarded conditional UPDATE (`WHERE exceptions.id = ? AND status = expectedFromStatus` → 0 rows ⇒ `Conflict("STALE_EXCEPTION")`), `writeAudit(tx, ...)`, then return the reloaded detail (`loadTripDetail(tx, tripId)` so the trip's exception list + recomputed SLA refresh). Reason-code defaults pre-fill `severity`/`responsible_party` at create (overridable). `owner_user_id` defaults to the creating actor, required, reassignable.

**Rationale**: directly encodes FR-009's legal transitions and FR-008's owner rules; mirroring `transitionTripStatus`/`cancelTrip` (RECON: pre-tx legality → guarded UPDATE 0-rows⇒`Conflict` → `writeAudit` → reload) keeps one proven transaction shape (DRY). `EXCEPTION_SEVERITIES`/`EXCEPTION_STATUSES`/`EXCEPTION_RESPONSIBLE_PARTIES` are **enums in the DB** (R0) consumed in Zod via `z.enum(...)` (RECON: the `z.enum(ARRAY, {message})` form). The 5-value responsible-party set is **its own enum**, never reusing `cancellation_responsible_party` (the spec's explicit clarification — only 4 values there, missing `force_majeure`).

**Alternatives rejected**: an exception-status state-machine table in the DB (the legal map is tiny and code-owned like `TRANSITIONS` in `trip-status.ts` — a pure helper is the established pattern); allowing reopen from terminal (FR-009 forbids — recurrence = new exception); reusing `cancellation_responsible_party` (4 values, no `force_majeure` — spec rejects).

## R9 — Milestone recording: reuse `transitionTripStatus`; free-form note service (FR-001/003/005)

**Decision**: Milestone recording **reuses 003's `transitionTripStatus(tripId, args: TransitionTripInput, actorUserId): Promise<TripDetail>`** (RECON: that is the actual symbol; the spec's "transitionTrip" is the same service) — it already does the concurrency guard, status-machine legality, the `status_change` `trip_events` row, and the `trip.status_change` audit. 007 does **not** redefine the machine. The milestones drive these existing transitions in order: **`confirmed→at_origin→[loading]→loaded→in_transit→at_destination→[unloading]→unloaded→completed`** (all legal edges per the `TRANSITIONS` table in `trip-status.ts`; `loading`/`unloading` skippable). Milestone calls pass `source:'operator_manual'`. A **new** free-form note service `addTripNote(tripId, input, actorUserId): Promise<TripDetail>` in `packages/db/src/trips/trip-events.ts` inserts a `trip_events` row with `event_type='note'` (R6), `source='operator_manual'`, `notes`, optional `location_id`, optional `exception_id`, **no status change**, plus a `trip.note` audit row — same transaction shape, returns `loadTripDetail(tx, tripId)`. Planned-vs-actual (FR-005) is derived in the read/UI layer from the trip's `planned_pickup_window_*`/`planned_delivery_window_*` vs the recorded milestone `event_timestamp` (no new storage).

**Rationale**: FR-003 mandates milestone recording goes through the existing transition service (no re-implementation — DRY, Constitution III). The note path is the **one** net-new event-writing service (it needs the `note` event-type from R6); it reuses the audit + reload building blocks. After every milestone transition the on-change SLA recompute (R11) runs so `sla_status`/`sla_reasons` reflect the new state immediately.

**Alternatives rejected**: a new milestone-specific service that duplicates the transition logic (FR-003 forbids — reuse `transitionTripStatus`); recording notes as `status_change` with null statuses (corrupts timeline semantics — R6); storing planned-vs-actual deltas as columns (derivable from existing planned windows + event timestamps — YAGNI).

## R10 — The worker (first scheduled job): pg-boss, one process, one ~5-min sweep (FR-019/023)

**Decision**: Use **pg-boss** (already the chosen, installed queue — `workers/package.json` deps `pg-boss ^12.18.2`; `graphile-worker` is absent), the **existing single `@brazil-tms/workers` process** (`workers/index.ts` → `createBoss → boss.start → setupQueues → registerJobHandlers`). Add **ONE scheduled job** (the first ever) via pg-boss's built-in cron (`boss.schedule(name, cron, data, options)` — STACK §3.11 "scheduling via the queue's built-in cron, no separate scheduler service"), default cadence **~5 min, configurable** via an env var (`SLA_SWEEP_CRON`/cadence, added to `workers/.env` + `infra/supabase/docker-compose.yml` worker env). New job folder `workers/jobs/sla-sweep/` (`index.ts` exporting `runSlaSweep(payload)` + `registerSlaSweep(boss)`, mirroring the import-job convention) registered with one line in `workers/jobs/index.ts`. The sweep, over **active (non-terminal) trips only** (`ACTIVE_TRIP_STATUSES` from `@brazil-tms/shared`), in **chunks** (e.g. 200/batch for low-thousands scale): (a) **recomputes `sla_status`/`sla_reasons`** per trip with **per-trip fault isolation** (try/catch per trip — skip-and-continue, log the per-trip error, never abort the sweep); (b) **generates + auto-resolves alerts idempotently** (`ON CONFLICT DO NOTHING` for generation; conditional UPDATE for auto-resolve). Per-trip concurrency with the BFF on-change recalc uses **`SELECT ... FOR UPDATE`** on the trip row inside each per-trip tx (last-writer-wins on identical deterministic evaluator inputs — both compute the same answer). Observability: a structured **per-sweep summary log** (`duration_ms`, `evaluated`, `changed`, `alerts_created`, `alerts_resolved`, `errors`) + a **last-run heartbeat** (e.g. a single-row `worker_heartbeat`/log line). New job-name+payload contract added to `@brazil-tms/shared` (a new `domain/`/`sla/jobs.ts` sibling of `import/jobs.ts`, pure, shared by BFF + worker). Queue name added to the `setupQueues` loop.

**Rationale**: STACK §3.11 + the constitution mandate **Postgres-backed queue + ONE Node worker, no Redis/BullMQ/Edge Functions** — pg-boss is already committed (RECON), so 007 **adds to** the existing infra, it does not build a new one. **Constitution I justification for the worker**: the worker package/process is the **constitutionally pre-declared background mechanism** (built by 004 for imports); 007 is the **first in-scope need for a scheduled sweep** (time-based risk like a passed confirmation cutoff must surface with no user action — FR-019/SC-006), not speculative. Per-trip fault isolation + `FOR UPDATE` + idempotent `ON CONFLICT` make the sweep safe to run concurrently with the synchronous BFF recalc (R11). Chunking handles the stated low-thousands active-trip scale without long-running locks.

**Alternatives rejected**: graphile-worker (not installed; pg-boss already chosen — switching is churn with no benefit); a separate cron service / OS cron (STACK §3.11 forbids — use the queue's built-in cron); a second worker process or microservice (Constitution — one app + one worker); aborting the whole sweep on one bad trip (violates fault isolation — skip-and-continue).

## R11 — On-change recalc path: synchronous, single-trip, in the mutation transaction (FR-019)

**Decision**: A shared single-trip recompute `recomputeTripSla(tx, tripId, actorUserId)` in `packages/db/src/trips/sla.ts` that (1) loads the trip's planned windows + current status + `currentStatusEnteredAt` + 006 `assignmentPresent`/`confirmedAt` + open-high-severity-exception count, (2) resolves the applicable `customer_sla_rules` row (R3) or falls back to `DEFAULT_SLA_POLICY` (R7), (3) calls `evaluateSlaRisk(ctx, rule)`, (4) writes `sla_status`/`sla_reasons` atomically (R5). It is invoked **synchronously inside the mutation transaction** of every state-changing service that affects risk — milestone (`transitionTripStatus` extended to call it, or its 007 callers), exception create/transition, and (read-only-input) on assignment/confirmation changes (006 services gain the call, or 007 wraps them). This gives the spec's "immediate UI truth" (SLA flips the instant the change commits, before any poll). The **high-severity-exception alert** is generated **synchronously in the BFF/service on exception create** (so it appears immediately), with the worker as **backstop + auto-resolver** — safe because generation is `ON CONFLICT DO NOTHING` on the partial-unique (R4). Time-based-only alerts (passed cutoff, missed arrival with no triggering user action) are generated **by the worker sweep** (R10).

**Rationale**: FR-019 requires recalc **on relevant changes AND** periodically; the on-change path is synchronous so the mutating user sees correct risk immediately (no poll lag), the worker covers purely time-based transitions. One shared `recomputeTripSla` (DRY) is called from every relevant service; the evaluator is the single source (R7). Synchronous high-severity-exception alert + worker backstop + `ON CONFLICT DO NOTHING` means no double-fire and no missed fire (FR-024 idempotency holds across both paths).

**Alternatives rejected**: recalc only in the worker (violates "immediate UI truth" — a milestone wouldn't flip risk until the next sweep); enqueuing an async recalc job on every change (adds latency + a queue round-trip for a sub-millisecond pure computation — synchronous in-tx is simpler, KISS); generating ALL alerts synchronously (time-based alerts have no triggering mutation — the worker must own those).

## R13 — Audit actions (FR-028, i18n guard)

**Decision**: Add to `packages/shared/src/audit/actions.ts` — the `AuditAction` union **and** `ALL_AUDIT_ACTIONS` array (kept in lockstep) — these new strings: `exception.create`, `exception.update`, `exception.resolve`, `exception.cancel`, `trip.note`, `sla_rule.create`, `sla_rule.update`. **Milestone/status changes reuse the existing `trip.status_change`** (no new action — they go through `transitionTripStatus`). SLA recompute writes are **not** separately audited (they are a derived projection, not a user action — the triggering mutation is audited; this keeps audit noise down and matches "assignment changes audited, derived state not"). Alert generate/acknowledge are **not** in the `AuditAction` union (worker-generated operational notices, not user domain mutations; acknowledgement is view triage) — they are tracked on the `alerts` row itself (`acknowledged_by_user_id`/`acknowledged_at`). Each new action needs i18n labels in **both** `Trips.auditActions` (nested — e.g. `Trips.auditActions.exception.create`, `Trips.auditActions.trip.note`) **and** flat `AuditActions` (`exception_create`, `exception_update`, `exception_resolve`, `exception_cancel`, `trip_note`, `sla_rule_create`, `sla_rule_update`) — never a dotted key.

**Rationale**: `messages.test.ts` enforces (a) **no key contains "."** (next-intl nesting separator — dotted keys throw `INVALID_KEY` and break every render, per MEMORY), and (b) every `ALL_AUDIT_ACTIONS` entry has a flat `AuditActions` label (the global audit screen looks up `action.replaceAll(".","_")`). Both must pass — so each new action gets nested + flat labels. Reusing `trip.status_change` for milestones (vs a new `trip.milestone`) is DRY — the transition service already writes it. Not auditing the SLA projection / alerts as `AuditAction`s avoids audit-log spam from the 5-min sweep (worst-state-wins recompute is deterministic derived state).

**Alternatives rejected**: a `trip.milestone` action (milestones ARE status changes — `trip.status_change` already covers them); auditing every SLA recompute (the worker sweep would flood `audit_logs` every 5 min — derived state, not a user action); putting alert acknowledgement in `AuditAction` (it is view triage, recorded on the alert row — not a domain mutation needing the global audit screen).

## R16 — Performance, freshness, scale (SC-005/006, FR-030)

**Decision**: Freshness = **polling** reusing 005's cadences — board `CONTROL_TOWER_POLL_MS = 30s`, dashboard `DASHBOARD_POLL_MS = 60s`, detail `TRIP_DETAIL_POLL_MS = 30s` (RECON: `apps/web/lib/trips/client.ts`), plus the Exception Management list and alert list on the board/30s cadence; new client hooks invalidate the `["trips"]` root (and a new `["alerts"]`/`["exceptions"]` root) following the `useMutation`+`invalidateQueries` pattern. **No Realtime** (FR-030). Worker sweep cadence **~5 min default, configurable** (R10). Scale: **low-thousands of active trips**, the sweep **chunked** (≤200/batch) with per-trip `FOR UPDATE` (R10). Targets: the pure SLA evaluator is sub-millisecond per trip; on-change recompute adds negligible time inside the mutation tx; Exception Management list and the board load within ~3 s at medium scale (inheriting 005's targets), backed by the `exceptions_*`/`alerts_*`/`customer_sla_rules_*` indexes (R1–R4) and the existing trip/board indexes. The 5-min sweep over low-thousands chunked trips completes well inside the cadence (per-sweep summary log proves it — R10).

**Rationale**: medium/low-thousands scale inherited from 005/006; indexed reads + a pure in-memory evaluator + chunked sweep keep every surface within target without Realtime (Constitution / STACK §3.10–§3.11). Polling reuse means zero new freshness mechanism.
