# Feature Specification: Documents, Completion, Billing Readiness, Rates, and Export

**Feature Branch**: `008-documents-billing-export`

**Created**: 2026-05-31

**Status**: Draft

**Input**: User description: "Users can attach proof documents, validate completion, mark trips billing-ready, maintain simple rates, and export billing-ready trips. Documents carry type, file, upload user, upload timestamp, notes, external reference, and verification status (accepted/rejected/pending review). Customer-specific document checklists determine completion and billing blockers. A trip can be marked Completed only when completion rules are satisfied and Billing Ready only when billing-ready rules are satisfied. Finance can configure simple rates by customer, lane, vehicle type, and effective date; billing supports tolls, waiting time, redelivery, extra stops, penalties, discounts, and manual adjustments; finance can export billing-ready trips to CSV or spreadsheet; export batch history is recorded. Worker jobs: billing export generation and missing-document checks. Per-customer required proof documents, the finance export format, and billing rules are gated business inputs — if missing, allow manual values and mark the affected sign-off as blocked, never invent them. Store binary files in Supabase Storage and metadata in Postgres. Out of scope: mobile photo upload, OCR/extraction, customer-specific invoice layouts, ERP/accounting integration, and an advanced billing engine beyond simple rates plus manual adjustments."

**Source PRD sections**: §11.6, §11.7, §13.1, §13.9, §13.11, §14.1, §15.9, §15.10, §17 (cases 7–8), §19.3, §19.4, §20.3, §20.4, §22 (Phase 4), §23, §29 (Inputs #3, #4, #5), §30

New tables (migration `0007`): **`documents`**, **`document_requirements`**, **`document_types`** (configurable proof-document-type master), **`rates`**, **`billing_items`** + a sibling **`billing_adjustments`** line table (the BILL-004 typed adjustments — the Billing Item's table shape was deferred to planning, which decomposed it into a child line table), and **`export_batches`** (so the `0007` migration creates **seven** tables); binaries live in **Supabase Storage** (metadata-only in Postgres, STACK §3.9). New worker jobs on the existing worker: an **on-demand `billing-export`** job (heavy file generation off the request path, STACK §3.11/§3.12) and a **periodic `document-checks`** sweep that flags completed trips missing required documents and feeds the dashboard widget + the two §17 alerts. Open items are **gated business inputs / deferred slice inputs, not blockers and not invented** (Constitution II): per-customer required proof documents (§29 Input #3 — checklist sign-off **blocked** until supplied; evaluator runs on a configurable default checklist), the finance billing export format (§29 Input #4 — export uses a **labeled default column set**, export sign-off **blocked** until the exact layout is supplied), and per-customer billing rules for tolls/waiting-time/penalties/cancellation (§29 Input #5 — billing accepts **manual values/adjustments**, billing-rule sign-off **blocked** until supplied). It builds on `specs/001-platform-access-shell/` (auth, audit, i18n, the permission catalog whose six document/billing keys it first enforces), `specs/002-master-data-config/` (customers/lanes/vehicle types; `manage_commercial_data`), `specs/003-trip-domain-lifecycle/` (the `trip_status` enum, `transitionTripStatus` service, `billingStatus` projection, append-only `trip_events`, and the `document/rate/billing-export columns (008)` anchor it left), `specs/004-trip-import-validation/` (the Import Batch durable-batch + worker-job pattern Export Batch mirrors), `specs/005-control-tower/` (the Trip-Detail documents/billing placeholders, the Billing/Documents navigation surfaces, the "Missing documents" board view, and the "Completed trips missing documents" dashboard widget this slice fills), and `specs/007-execution-events-exceptions/` (the in-app `alerts` store + idempotent generation framework, and the attachment-storage surface this slice provides).

## Overview & Intent *(why this feature exists)*

Slices 003–007 take a trip all the way from import to "Unloaded" with a live SLA/exception picture — but the trip cannot yet be **closed out**, **proven**, or **billed**. Slice 005 deliberately left the Trip-Detail **documents** and **billing-detail** sections as empty placeholders "until Feature 008", and registered a **"Missing documents"** board view and **"Completed trips missing documents"** dashboard widget as labelled placeholders for this slice to fill (the **"Billing pending count"** widget and billing-status filter already ship **live** in 005, since the billing-phase statuses existed from slice 003). Slice 003 created the single `trip_status` machine already containing `completed → billing_pending → billing_ready → billed`, made billing status a **projection** of that status (not a second field), and explicitly reserved **"document/rate/billing-export columns (008)"**. Slice 007 wired the in-app **alert** framework but **deferred two §17 alert cases** ("completed but missing required documents", "billing item blocked by missing proof") and **deferred exception/event attachments** because the **document storage surface did not exist yet**. This feature delivers that surface: operations attach **proof of execution** (POD, CT-e/MDF-e references, gate receipts), finance and ops **verify** it, the system **gates Completed and Billing Ready** on the customer's required-document checklist and pricing data, finance maintains **simple rates** and a transparent **billable breakdown**, and finance **exports** clean billing-ready trips with **durable export-batch history**.

The value is a **clean, defensible billing close** — revenue protected from leakage and disputes (PRD §24 risk: "Missing documents delay billing → revenue leakage and disputes"). The mechanism is **gating, not data entry**: a trip cannot reach **Completed** while its completion-required documents are missing, and cannot reach **Billing Ready** while its billing-required documents are missing, its pricing is absent, or an open billing dispute is unresolved — unless an authorized user records a per-document **unavailable-with-reason** waiver (audited). Completion and Billing Ready are **transitions on slice 003's existing status machine** (its concurrency guard, legal-transition table, and audit/`trip_events` write), never a new lifecycle; billing status is the **`billingStatus(current_status)` projection** 003 already defines. Heavy **export generation runs on the worker** off the request path (STACK §3.11/§3.12), writing the file to **Supabase Storage** and a durable **Export Batch** record (BILL-008) that mirrors slice 004's Import Batch. Freshness on every surface is **polling via TanStack Query** — never Realtime (STACK §3.10).

Customer variation is **config-driven** (Constitution): one document-requirement checklist engine parameterized **per customer**, one rate table keyed by **customer/lane/vehicle-type/effective-date**, and one export engine driven by a **configurable column set** — never per-customer code or per-customer invoice layouts (those are Later, BILL-009). Where a business input is missing it is made **configurable with an explicit default and the affected sign-off marked blocked** — never invented (Constitution II): per-customer required proof documents (§29 Input #3), the exact finance export format (§29 Input #4), and per-customer billing rules for tolls/waiting-time/penalties/cancellation (§29 Input #5) are all gated — the slice ships on labeled defaults + manual values and reports each affected sign-off as **blocked** until the business supplies the real inputs.

## Clarifications

### Session 2026-05-31 *(design decisions resolved while specifying; informed defaults — business-input gaps are recorded under "Blocked / Open for business sign-off")*

- Q: Which permission keys gate this slice's write surfaces, and does it add any? → A: **No new key.** It **first-enforces** six pre-declared 001 keys (owner-feature 008 in the matrix): **`upload_documents`** (record proof — Admin, Operations Manager, Dispatcher, Control Tower, Fleet Coordinator, Finance), **`verify_documents`** (accept/reject/pending — Admin, Operations Manager, Finance), **`mark_completed`** (mark a trip Completed — Admin, Operations Manager, Control Tower), **`mark_billing_ready`** (mark Billing Ready — Admin, Finance), **`edit_rates`** (maintain rates and billing values — Admin, Finance), and **`export_billing`** (run billing exports — Admin, Finance). Per-customer **required-document checklists** are per-customer commercial config, so they **reuse `manage_commercial_data`** (002 — Admin, Operations Manager), mirroring 007's reuse of the same key for per-customer SLA rules; **no `manage_documents`/`configure_billing` key exists or is added**. All **reads** (documents, checklist status, billing values, export history) stay on **`view_all_trips`**.
- Q: Are Completion and Billing Ready a new status machine? → A: **No — transitions on 003's existing machine.** `trip_status` (003) already contains `unloaded → completed → billing_pending → billing_ready → billed`; this slice drives those transitions through **003's `transitionTripStatus` service** (concurrency guard, legal-transition table, `trip_events` + audit write) and **does not redefine** the status machine. Marking **Completed** = `unloaded → completed` gated by `mark_completed` + §19.3 completion rules + completion-required documents; marking **Billing Ready** = `billing_pending → billing_ready` gated by `mark_billing_ready` + §19.4 billing-ready rules.
- Q: Is "billing status" a new stored field? → A: **No — it is 003's `billingStatus(current_status)` projection** (003 R3): billing status is *derived* from `current_status` when it is in `{billing_pending, billing_ready, billed, disputed}` (else null). This slice does not add a second billing-status column on the trip. The **Billing Item** record holds the *monetary* breakdown, dispute flag, period, and export linkage — not a parallel status machine. *(BILL-001)*
- Q: After a trip is marked Completed, how does it reach Billing Pending? → A: **Automatic follow-through.** Per §11.6 step 6 ("System marks trip as Billing Pending"), a successful completion transition **immediately advances** `completed → billing_pending` through the same 003 service, and a **Billing Item** is created/attached at billing-phase entry so finance has a record to price. This is an informed default (the §11.6 workflow), not a new rule.
- Q: Does a missing required document **block** or only **warn**? → A: **Configurable, default block.** §19.4/DOC-005/BILL-006 say "prevents *or* warns"; block-vs-warn is a **per-customer/company policy** (mirroring 006's configurable blocking-vs-warning). The **default is block** (revenue protection); a holder of the gating key (`mark_completed` / `mark_billing_ready`) may clear a specific missing document by recording it **unavailable with a reason** (audited). This keeps the gate meaningful without inventing a customer policy. *(Refined by Session 2026-06-01: the clear path is a **per-document "unavailable-with-reason" waiver**, not a blanket gate bypass — see FR-010.)*
- Q: How is the billable breakdown modeled (BILL-004/005)? → A: As **typed adjustment entries** on the Billing Item — each one of `toll`, `waiting_time`, `redelivery`, `extra_stop`, `penalty`, `discount`, `manual_adjustment` carries an **amount** (integer minor units) + **note**; the system shows **planned value** (rate-derived, from the matching rate's base amount), **executed value** (the **base freight actually applied** to this trip — the rate-derived amount, or the **manual billing amount** when no rate matches; this is the "base freight" term in the formula below, following PRD §14's planned-vs-executed convention), **adjustment value** (sum of typed entries), and **final billable value** = base freight + tolls + extras + penalties − discounts ± manual adjustments. Monetary values are **integer minor units + currency (BRL default)** per §14 conventions. The physical decomposition (typed columns vs a child adjustment-line table) is left to `/speckit-plan`; the spec fixes the **behavior**, not the table shape.
- Q: Is Export Batch a separate entity or folded into Billing Item? → A: **Separate entity**, mirroring slice 004's **Import Batch**. The Billing Item links to it via `export_batch_id`; an export run creates one **Export Batch** (customer, period, format, file location, generated-by/at, trip count, totals, status) satisfying BILL-008's "export batch history". On a successful export the included trips transition **`billing_ready → billed`** through the 003 service; whether export **locks** (transition to `billed`) or only **flags** exported trips is configurable per §11.7 step 7, **default = mark Billed**.
- Q: How is a rate selected when several match a trip (BILL-002/003)? → A: **Most-specific, currently-effective wins**, mirroring 007's SLA-rule precedence: a rate matches on **customer + lane + vehicle type** within its **effective window**; precedence is **lane-and-vehicle-type-specific > lane- or vehicle-type-only > customer-default**, tie-breaking on the latest `effective_start`; a rate outside its effective window is not selected. When **no rate matches**, the planned freight is left for a **manual billing amount**, and billing-rule sign-off is reported **blocked** (§29 Input #5).
- Q: What lights up §17 alert cases 7–8 that slice 007 deferred? → A: **This slice, via 007's existing `alerts` store** (not a new alert system). The `document-checks` worker sweep generates, through 007's **idempotent per-(trip, case)** generation + **auto-resolve** framework, the **"trip completed but missing required documents"** alert (§17 case 7) and the **"billing item blocked by missing proof"** alert (§17 case 8). Both stay **in-app only** (no external channel), consistent with 007's scope boundary.
- Q: Where do document and export **binaries** live? → A: **Supabase Storage**; only **metadata/references** live in Postgres (STACK §3.9 — "store file metadata in Postgres; store binary files in object storage; do not store documents inside Postgres; document access must follow trip/customer permissions"). This slice provides the storage surface whose absence 007 deferred exception/event attachments against; attachment **back-fill** for 007 exceptions/events is a non-blocking follow-on, not in this slice's acceptance bar.
- Q: Which worker jobs are added, and is a new worker/queue introduced? → A: **No new worker process or queue.** Two jobs run on the **existing single Node worker + `pg-boss`**: an **on-demand `billing-export`** job (queued when finance requests an export; heavy CSV/XLSX generation off the request path, durable Export Batch status — STACK §3.11/§3.12) and a **periodic `document-checks`** sweep (configurable default cadence ~5 minutes, mirroring 007's SLA sweep) that flags completed trips missing required documents for the dashboard widget and the two §17 alerts.

### Session 2026-06-01 *(clarification pass before planning)*

- Q: How is a trip's **billing period** determined for grouping, the pending/ready lists, and export? → A: **Month of completion.** The Billing Item's `billing_period` is **derived from the completion date (calendar month)**, **stored** on the Billing Item and **editable** by finance; the Billing screen and export **filter by customer + period**. This reconciles §14.1's "Billing period" field with §11.7's "select customer and billing period".
- Q: Are **proof-document types** a configurable master list or a fixed code enum? → A: **Configurable admin-managed master list** — a Document Type master (mirroring 007's `reason_codes`, managed via `manage_commercial_data`), referenced by both per-customer checklists and uploaded documents, **seeded** with defaults (POD, CT-e, MDF-e, gate receipt, customer-portal reference) and extensible **without code changes** (config-driven variation, Constitution). Adds the `document_types` master table.
- Q: When a required document **genuinely can't be provided**, how is that requirement satisfied to allow Completed / Billing Ready? → A: **Per-document "unavailable with a reason".** A gate-key holder may mark a **specific** required document **unavailable with a reason** (an audited waiver capturing who/when/why), which satisfies **that one** requirement while the gate **still checks the rest** — matching §11.6 step 2 ("marks unavailable with reason") and §19.4 ("approved exception"). This **replaces** the earlier blanket transition-override framing; an accepted document or such a waiver are the only two ways to satisfy a requirement.
- Q: What **file-type and size limits** apply to document uploads? → A: **Configurable allowed-type list (default PDF/JPG/PNG)** and a **configurable maximum size (default ~10 MB)**; disallowed types or oversize files are **rejected** with a clear message and nothing is stored. Both limits are configurable, not gated business inputs.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Attach and verify proof-of-execution documents (Priority: P1)

An operations or finance user opens a trip's **documents section** (filling slice 005's placeholder) or the **Documents** screen, **uploads** a proof file (POD, gate receipt, signed CT-e/MDF-e), choosing its **document type** and recording an **external reference** (CT-e number, MDF-e number, POD reference, gate receipt number, or customer-portal reference) and **notes**. The binary is stored in **Supabase Storage**; the metadata (type, file location, uploader, timestamp, reference, verification status) is stored in Postgres. A reviewer then marks each document **accepted**, **rejected**, or **pending review**, recording who verified it and when. Documents can be **downloaded** and the trip shows its **missing-document list** against the customer's checklist.

**Why this priority**: Proof is the foundation everything else in this slice gates on — completion, billing readiness, and the missing-document alerts all read document state. Without documents there is nothing to verify, nothing to gate, and nothing to prove at billing. It is also the first surface to fill slice 005's reserved Trip-Detail documents placeholder.

**Independent Test**: On a seeded trip, as a user with `upload_documents`, upload a file with a type and external reference; assert the binary lands in Supabase Storage and the metadata row captures type, file location, uploader, upload timestamp, external reference, notes, and an initial **pending review** status. As a user with `verify_documents`, mark it accepted/rejected; assert verifier and verified-timestamp persist and the status changes. Assert a user **without** `upload_documents` cannot upload and one **without** `verify_documents` cannot change verification status, and that the Documents screen lists the trip's documents and its outstanding required-document list.

**Acceptance Scenarios**:

1. **Given** a trip and a user with `upload_documents`, **When** they upload a document with a **type, file, external reference, and notes**, **Then** the binary is stored in object storage and a metadata record captures **type, file location, uploader, upload timestamp, external reference, notes**, and an initial verification status of **pending review**. *(DOC-001, DOC-002, DOC-006, §13.9, §20.3)*
2. **Given** an uploaded document and a user with `verify_documents`, **When** they mark it **accepted**, **rejected**, or **pending review**, **Then** the verification status updates and the **verifier and verified timestamp** are recorded. *(DOC-004, §13.9)*
3. **Given** a document stored in object storage, **When** an authorized user requests it, **Then** they can **download** it, and access follows the same trip/customer read permission as the rest of the trip. *(§15.9, STACK §3.9)*
4. **Given** a customer with a required-document checklist, **When** a user views the trip's documents section or the Documents screen, **Then** the **missing-document list** shows which required types are not yet accepted. *(DOC-003, §15.9)*
5. **Given** a user **without** `upload_documents` (or **without** `verify_documents`), **When** they attempt to upload (or verify), **Then** the action is refused and no document/verification change occurs. *(§16, §18)*
6. **Given** a stored document, **When** it is superseded or no longer needed, **Then** it is **archived/soft-deleted (never hard-deleted)** and remains in audit history. *(§14 conventions, STACK §5.4)*

### User Story 2 - Validate completion and mark Billing Ready under enforced rules (Priority: P1)

An operations user marks a fully executed trip **Completed** — allowed only when the §19.3 completion rules hold (required milestones recorded or an exception reason provided, not cancelled, unloading complete, operational closure fields present) **and** the customer's **completion-required** documents are satisfied; the system then advances the trip to **Billing Pending** and creates its Billing Item. A finance user later marks it **Billing Ready** — allowed only when the §19.4 rules hold (completed, billing-required documents accepted or waived via an audited per-document waiver, a rate or manual billing amount exists, no open billing dispute, finance confirms review). A missing required document **blocks** the relevant transition (configurable; default block) unless a gate-key holder records that specific document **unavailable with a reason** (audited). A periodic worker sweep surfaces trips that have passed completion but still miss required documents on the dashboard and as the two §17 alerts.

**Why this priority**: "Completed trips can be marked billing pending" and "Finance can validate and export billing-ready trips" are explicit MVP acceptance criteria (§23) and the Phase-4 exit bar (§22). Gating is the whole point of the slice — it is what protects revenue from missing proof — so it is P1, built directly on US1's document state and 003's status machine.

**Independent Test**: Seed a trip at `unloaded` with a customer checklist. With completion-required docs missing, attempt to mark Completed as a `mark_completed` holder → blocked; satisfy the docs (or mark a missing one **unavailable with a reason**) → trip becomes `completed` then auto-advances to `billing_pending` with a Billing Item. With billing-required docs missing / no rate / open dispute, attempt Billing Ready as a `mark_billing_ready` holder → blocked; satisfy the rules → trip becomes `billing_ready`. Assert every transition is a 003 status-machine transition (records a `trip_events` row + audit), that the unavailable-with-reason waiver records who/when/why, that the dashboard "Completed trips missing documents" count and the §17 alerts reflect the missing-doc trip, and that users lacking the keys are refused.

**Acceptance Scenarios**:

1. **Given** a trip at `unloaded` whose §19.3 rules are met and whose completion-required documents are accepted, **When** a user with `mark_completed` marks it Completed, **Then** the trip transitions to **`completed`** via the 003 service (recording a `trip_events` row + audit) and **automatically advances to `billing_pending`** with a **Billing Item** created. *(BILL-001, §19.3, §11.6; reuses 003)*
2. **Given** a trip whose **completion-required documents are missing**, **When** a user attempts to mark it Completed, **Then** the transition is **blocked** by default with a clear reason — **unless** a gate-key holder records the specific missing document as **unavailable with a reason** (audited), which satisfies that requirement. *(DOC-003, DOC-005, §19.3, §11.6)*
3. **Given** a trip at `billing_pending` whose §19.4 rules are met (billing-required documents accepted, a rate or manual amount exists, no unresolved billing dispute), **When** a user with `mark_billing_ready` marks it Billing Ready, **Then** the trip transitions to **`billing_ready`** via the 003 service and the billing status projection reflects it. *(BILL-001, BILL-006, §19.4)*
4. **Given** a trip at `billing_pending` whose **billing-required documents are missing or whose pricing is absent or which has an open billing dispute**, **When** a user attempts Billing Ready, **Then** it is **blocked/warned** (configurable; default block); a missing required document is cleared only by an **accepted upload** or an audited **unavailable-with-reason** waiver, and the pricing and dispute gates must likewise be satisfied. *(DOC-005, BILL-006, §19.4)*
5. **Given** a trip that has **passed completion** (now `billing_pending`) but still has **required documents unsatisfied**, **When** the `document-checks` worker sweep runs, **Then** the trip is counted in the dashboard **"Completed trips missing documents"** widget and an in-app **§17 alert** is generated (case 7, and case 8 once a Billing Item is blocked) via 007's idempotent alert framework — **in-app only**. *(§15.2, §17 cases 7–8; reuses 007)*
6. **Given** a user **without** `mark_completed` (or **without** `mark_billing_ready`), **When** they attempt the corresponding transition, **Then** it is refused and the trip is unchanged. *(§16, §18)*

### User Story 3 - Configure per-customer required-document checklists (Priority: P2)

An Operations Manager (or Admin) configures, per customer, **which document types are required** and whether each one **blocks Completed** (required for completion) and/or **blocks Billing Ready** (required for billing), optionally scoped by **vehicle type or lane**, with an active flag. These checklists drive the gating in US2 and the missing-document lists/alerts. Until a customer's real required-document list is supplied (§29 Input #3), the system runs on a **configurable default checklist** and that customer's **document-checklist sign-off is marked blocked**.

**Why this priority**: The checklist parameterizes US2's gating, but the gated business input (§29 Input #3) means the system must run on defaults first; configuring the real per-customer list is the path to lifting the block, so P2 — mirroring slice 007's per-customer SLA-rule story.

**Independent Test**: As a user with `manage_commercial_data`, create a customer's required-document checklist marking one type completion-blocking and another billing-blocking; assert US2 gating uses it for that customer's trips while customers with no checklist fall back to the default and are reported **document-checklist sign-off blocked**; assert a user without `manage_commercial_data` cannot edit checklists.

**Acceptance Scenarios**:

1. **Given** a user with `manage_commercial_data`, **When** they define a customer's required document types and mark each **required-for-completion** and/or **required-for-billing** (optionally scoped by lane/vehicle type), **Then** the checklist is saved and used by US2's completion/billing gating for that customer. *(CUST-004, DOC-003)*
2. **Given** a customer with **no configured checklist**, **When** a trip for that customer is evaluated, **Then** the **default checklist** applies and the customer is reported as **document-checklist sign-off blocked**. *(§29 Input #3; Constitution II)*
3. **Given** a checklist entry scoped to a lane or vehicle type, **When** a trip matches that scope, **Then** the scoped requirement applies in addition to/over the customer default. *(CUST-004, §14.1)*
4. **Given** a user **without** `manage_commercial_data`, **When** they attempt to edit a customer checklist, **Then** the action is refused. *(§16, §18)*

### User Story 4 - Maintain simple rates and compute the billable breakdown (Priority: P2)

A finance user maintains **simple rates** keyed by **customer, lane, vehicle type, and effective date** (base amount + currency, with optional toll/waiting-time/extra-stop handling rules). On a trip's **billing section** (filling slice 005's placeholder) the system computes the **planned freight amount** from the matching rate, and finance adds typed **adjustments** — tolls, waiting time, redelivery, extra stops, penalties, discounts, and manual adjustments — so the trip shows **planned value, executed value, adjustment value, and final billable value**. When no rate matches, finance enters a **manual billing amount** and billing-rule sign-off is reported blocked.

**Why this priority**: Rates and the billable breakdown are required for Billing Ready (a rate or manual amount must exist, §19.4) and for export, but the system functions on manual values until finance rules land (§29 Input #5), so configuring real rates/rules is P2.

**Independent Test**: As a user with `edit_rates`, create a rate for a customer/lane/vehicle-type/effective-date; on a matching trip assert the planned freight is computed from it; add one of each adjustment type and assert the final billable value = base + tolls + extras + penalties − discounts ± manual adjustments and that planned/executed/adjustment/final are all shown; on a trip with no matching rate assert a manual amount is accepted and billing-rule sign-off is reported blocked; assert a user without `edit_rates` cannot edit rates or billing values.

**Acceptance Scenarios**:

1. **Given** a user with `edit_rates`, **When** they create a rate for a **customer + lane + vehicle type + effective date** (base amount + currency), **Then** the rate is saved and used to compute the **planned freight amount** for matching trips. *(BILL-002, BILL-003)*
2. **Given** several rates that could match a trip, **When** the planned freight is computed, **Then** the **most-specific, currently-effective** rate is applied (lane+vehicle-type > lane- or vehicle-type-only > customer-default; tie-break latest `effective_start`; outside its effective window it is not selected). *(BILL-002, BILL-003)*
3. **Given** a trip's Billing Item, **When** finance adds **tolls, waiting time, redelivery, extra stops, penalties, discounts, and manual adjustments**, **Then** each typed adjustment (amount + note) is recorded and the **final billable value** is recomputed. *(BILL-004)*
4. **Given** a priced trip, **When** finance views its billing section, **Then** it shows **planned value, executed value, adjustment value, and final billable value** in the trip currency (BRL default, integer minor units), where **executed value** is the applied base-freight term. *(BILL-005)*
5. **Given** a trip with **no matching rate**, **When** finance prepares billing, **Then** a **manual billing amount** is accepted and the customer's billing-rule sign-off is reported **blocked** (defaults used, never invented). *(§29 Input #5; Constitution II)*
6. **Given** a user **without** `edit_rates`, **When** they attempt to edit a rate or a billing value, **Then** the action is refused. *(§16, §18)*

### User Story 5 - Export billing-ready trips and record export-batch history (Priority: P2)

A finance user works the **Billing** screen's **billing-pending** and **billing-ready** lists, selects a **customer and billing period**, reviews the **billing-ready** trips and their computed values (with missing-proof warnings), and triggers an **export to CSV or spreadsheet**. The heavy file generation runs on the **worker**, writing the file to **Supabase Storage** and creating a durable **Export Batch** record (customer, period, format, file location, generated-by/at, trip count, totals, status). Exported trips are then **locked or flagged** (configurable; default: transition `billing_ready → billed`). The Billing screen shows **export-batch history**.

**Why this priority**: Export is the slice's terminal outcome ("Finance can generate billing-ready exports", §22 Phase-4 exit), but it depends on US1–US4 (documents, completion, rates) being in place first, and the exact column layout is a gated input (§29 Input #4), so P2.

**Independent Test**: Seed billing-ready trips for a customer/period. Open the Billing screen and assert the pending list shows `billing_pending` trips and the ready list shows `billing_ready` trips, filterable by customer/period. As a user with `export_billing`, trigger an export; assert a `billing-export` worker job runs, a file is written to Supabase Storage, an **Export Batch** record captures customer/period/format/file/generated-by/at/trip-count/totals/status, that exported trips are marked **billed** (or flagged, per config), that the export uses the **labeled default column set** with export sign-off reported **blocked** until §29 Input #4 lands, and that a user without `export_billing` cannot export. Assert the export does not run synchronously inside the request handler.

**Acceptance Scenarios**:

1. **Given** billing-ready trips for a customer and period and a user with `export_billing`, **When** they trigger an export to **CSV or spreadsheet**, **Then** a **worker** job generates the file (off the request path), stores it in object storage, and records an **Export Batch** with customer, period, format, file location, generated-by/at, trip count, totals, and status. *(BILL-007, BILL-008, §11.7, §15.10, STACK §3.11/§3.12)*
2. **Given** a completed export, **When** it finishes, **Then** the included trips are **locked or flagged** per configuration — default: transitioned **`billing_ready → billed`** via the 003 service. *(§11.7 step 7; reuses 003)*
3. **Given** prior exports, **When** finance opens the Billing screen, **Then** the **export-batch history** is listed and each batch's file is retrievable. *(BILL-008, §15.10)*
4. **Given** the exact finance export format is **not yet supplied**, **When** an export runs, **Then** it uses a **labeled default column set** and the export sign-off is reported **blocked** until the format is provided. *(§29 Input #4; Constitution II)*
5. **Given** a billing period with trips still missing required proof, **When** finance reviews the billing list, **Then** those trips show **missing-proof warnings** on the billing-pending list and, because they cannot reach `billing_ready` (FR-009, §19.4), are **excluded from the billing-ready export**. *(BILL-006, §15.10)*
6. **Given** a user **without** `export_billing`, **When** they attempt to export, **Then** the action is refused. *(§16, §18)*

### Edge Cases

- **Completion with billing-required (not completion-required) docs missing**: the trip *can* be marked Completed (those docs do not block completion) and advances to `billing_pending`, but **cannot** reach Billing Ready until they are accepted — this is exactly how a "completed but missing required documents" §17 alert (case 7) becomes reachable.
- **Unavailable required document**: a gate-key holder (`mark_completed`/`mark_billing_ready`) may mark a specific required document **unavailable with a reason** (audited, per-document), which satisfies that one requirement without fabricating a file; the gate still checks the remaining requirements.
- **Rejected upload (type/size)**: an upload whose type is not in the allowed list (default PDF/JPG/PNG) or that exceeds the size cap (default ~10 MB) is **rejected** with a clear message and nothing is stored.
- **Rejected document**: a `rejected` document does **not** satisfy its checklist requirement; the requirement stays unmet (a rejected POD is treated as missing for gating).
- **No rate matches**: planned freight is left empty; a **manual billing amount** is required for Billing Ready, and billing-rule sign-off stays blocked (§29 Input #5) — values are never invented.
- **Rate effective-window gaps / overlaps**: when no rate is currently effective for a trip, there is no computed planned freight (manual amount path); when several overlap, the most-specific currently-effective rate wins (lane+vehicle-type > single-scope > customer-default; tie-break latest `effective_start`).
- **Cancelled trip**: a cancelled trip is not completable/billable; any documents already attached remain readable; no Billing Item progresses. Cancellation billing impact is owned by 003 (§19.5), not re-implemented here.
- **Open billing dispute**: a trip with an open billing dispute is **blocked** from Billing Ready until its `dispute_status` is set **resolved** (§19.4); the allow-without-resolving override, the full dispute-resolution workflow, and the `disputed` status round-trip are owned by 003/later, not this slice.
- **Re-export / partial period**: re-running an export for a period that already has billed trips does not double-bill — already-`billed` trips are excluded by default (configurable), and each export run is its own Export Batch record.
- **Export job failure**: a failed `billing-export` job records a useful error on the Export Batch (durable status) and does not leave trips half-transitioned; finance can retry. *(STACK §3.11)*
- **Missing-document sweep idempotency**: the `document-checks` sweep generates at most one active alert per (trip, case) via 007's partial-unique framework and auto-resolves it when the documents are completed — it does not re-spam.
- **Document binary vs metadata**: a document's binary lives only in Supabase Storage; deleting/replacing a file is a metadata-tracked, audited operation; binaries are never stored in Postgres (STACK §3.9).

## Requirements *(mandatory)*

### Functional Requirements

**Documents & proof of execution (DOC-001..DOC-006, §13.9, §15.9, §20.3)**

- **FR-001**: Authorized users (`upload_documents`) MUST be able to **upload a document to a trip**, with the **binary stored in Supabase Storage** and **metadata in Postgres** (never the binary in Postgres). Uploads MUST be validated against a **configurable allowed-type list (default PDF/JPG/PNG)** and a **configurable maximum size (default ~10 MB)**; a disallowed type or oversize file MUST be **rejected** with a clear message and nothing stored. *(DOC-001, STACK §3.9, §20.3)*
- **FR-002**: A document record MUST carry **document type, file location, external reference, uploaded-by, upload timestamp, notes, verification status, verified-by, and verified timestamp**; **external reference** MUST support values such as **CT-e number, MDF-e number, POD reference, gate receipt number, or customer-portal reference**; **document type** is drawn from the configurable **Document Type master** (FR-012). *(DOC-002, DOC-006, §13.9, §14.1)*
- **FR-003**: Verification status MUST be one of **accepted, rejected, pending review** (default **pending review** on upload); authorized users (`verify_documents`) MUST be able to set it, recording the **verifier and verified timestamp**. A **rejected** document MUST NOT satisfy a checklist requirement. *(DOC-004, §13.9)*
- **FR-004**: Authorized readers (`view_all_trips`) MUST be able to **download** a document; document access MUST follow the same trip/customer read permission as the trip. *(§15.9, STACK §3.9)*
- **FR-005**: The Trip-Detail **documents section** (filling slice 005's placeholder) and the **Documents** screen MUST list a trip's documents and show the **missing-document list** against the applicable customer checklist. *(§15.5, §15.9, DOC-003)*
- **FR-006**: Documents MUST be **soft-deleted/archived, never hard-deleted**, and document upload/verification/archival MUST produce **audit history**. *(§14 conventions, STACK §5.4)*

**Completion & Billing Ready gating (BILL-001, BILL-006, DOC-005, §19.3, §19.4, §11.6; reuses 003)**

- **FR-007**: Marking a trip **Completed** MUST be a **`transitionTripStatus` transition (`unloaded → completed`)** through slice 003's service (concurrency guard, `trip_events` + audit), gated by **`mark_completed`** and allowed only when the **§19.3 completion rules** hold **and** the customer's **completion-required documents** are satisfied. This slice MUST NOT redefine the status machine. *(BILL-001, §19.3, §11.6; reuses 003)*
- **FR-008**: On a successful completion, the system MUST **advance the trip to `billing_pending`** (§11.6 step 6) and **create/attach a Billing Item** so finance can price it; the Billing Item's **billing period** MUST default to the **calendar month of completion** (editable by finance), and the Billing screen and export MUST filter by **customer + period**. *(BILL-001, §11.6, §11.7)*
- **FR-009**: Marking a trip **Billing Ready** MUST be a **`transitionTripStatus` transition (`billing_pending → billing_ready`)** gated by **`mark_billing_ready`** and allowed only when the **§19.4 billing-ready rules** hold: trip completed, **billing-required documents accepted or waived** (an audited per-document unavailable-with-reason waiver per FR-010), a **rate or manual billing amount exists**, **no open billing dispute** (an open `dispute_status` blocks Billing Ready until it is set **resolved**; any allow-without-resolving override is owned by the deferred dispute-resolution workflow, §19.4), and finance confirms review. *(BILL-001, BILL-006, DOC-005, §19.4)*
- **FR-010**: An **unsatisfied** required document MUST **block or warn** the relevant transition; the behavior MUST be **configurable** (per-customer/company policy) with a **default of block**. A requirement is satisfied either by an **accepted document** OR by a gate-key holder recording that **specific** required document as **unavailable with a reason** — an **audited per-document waiver** (who/when/why) that satisfies **only that** requirement while the gate **still checks the rest** (PRD §11.6 "marks unavailable with reason", §19.4 "approved exception"). The system MUST NOT silently allow a gated transition. *(DOC-005, BILL-006, §19.4, §11.6; Constitution II)*
- **FR-011**: **Billing status MUST be the `billingStatus(current_status)` projection** owned by slice 003 (derived when `current_status ∈ {billing_pending, billing_ready, billed, disputed}`, else null); this slice MUST NOT introduce a second stored billing-status field on the trip. *(BILL-001; reuses 003 R3)*

**Per-customer required-document checklists (CUST-004, DOC-003, §13.1, §14.1)**

- **FR-012**: Authorized users (`manage_commercial_data`) MUST be able to maintain **per-customer required-document checklists**: which **document types** are required, each marked **required-for-completion** (blocks Completed) and/or **required-for-billing** (blocks Billing Ready), with optional **lane/vehicle-type scope** and an active flag. **Document types** themselves MUST be a **configurable admin-managed master list** (reused via `manage_commercial_data`, mirroring 007's `reason_codes`), referenced by both checklists and uploaded documents and seeded with defaults (POD, CT-e, MDF-e, gate receipt, customer-portal reference) — adding a type MUST NOT require code changes. *(CUST-004, DOC-003, §13.9, §14.1)*
- **FR-013**: Completion and Billing-Ready gating (FR-007/FR-009) MUST evaluate against the applicable customer checklist; where a customer has **no configured checklist**, the system MUST evaluate against a **configurable default checklist** and report that customer's **document-checklist sign-off as blocked** (never silently treat the default as signed off). *(CUST-004, DOC-003, §29 Input #3; Constitution II)*

**Rates & billing computation (BILL-002..BILL-005, §13.11, §15.10)**

- **FR-014**: Authorized users (`edit_rates`) MUST be able to maintain **simple rates** keyed by **customer, lane, vehicle type, and effective date** (base amount + currency, optional toll/waiting-time/extra-stop handling rules, active flag). *(BILL-002, §14.1)*
- **FR-015**: The system MUST compute a trip's **planned freight amount** from the **most-specific, currently-effective** matching rate (lane+vehicle-type > lane- or vehicle-type-only > customer-default; tie-break latest `effective_start`; a rate outside its effective window is not selected). When **no rate matches**, planned freight is left for a **manual billing amount**. *(BILL-002, BILL-003)*
- **FR-016**: A trip's **Billing Item** MUST support typed adjustments — **tolls, waiting time, redelivery, extra stops, penalties, discounts, and manual adjustments** — each with an **amount (integer minor units) + note**. *(BILL-004, §14.1)*
- **FR-017**: The billing section MUST show **planned value, executed value, adjustment value, and final billable value** in the trip currency (**BRL default**, integer minor units), where **final billable = base freight + tolls + extras + penalties − discounts ± manual adjustments** and **executed value** is the **base-freight term** of that formula (the rate-derived planned freight, or the manual billing amount when no rate matches), distinct from the rate-derived **planned value** when the two differ. *(BILL-005; §14.1 Billing Item fields; §14 conventions)*
- **FR-018**: When **per-customer billing rules** (toll/waiting-time/penalty/cancellation handling) are **not supplied**, the system MUST accept **manual values/adjustments** AND report that customer's **billing-rule sign-off as blocked** (never invent the rule). *(§29 Input #5; Constitution II)*

**Billing screen, export & export-batch history (BILL-001, BILL-006, BILL-007, BILL-008, §11.7, §15.10, §20.4)**

- **FR-019**: The **Billing** screen MUST provide a **billing-pending list** (trips whose billing-phase status is `billing_pending` — awaiting pricing/validation) and a **billing-ready list** (trips at `billing_ready`), each **filterable by customer and billing period** and showing each trip's **computed billable value** and a **missing-proof indicator**; from the pending list an authorized user opens a trip to price it and mark it Billing Ready (FR-009), and the ready list feeds the export selection (FR-020). Both are **read surfaces gated by `view_all_trips`** with **polling** freshness. *(§15.10, BILL-001, BILL-006)*
- **FR-020**: Authorized users (`export_billing`) MUST be able to **export billing-ready trips** for a **selected customer and billing period** to **CSV or spreadsheet**; the heavy file generation MUST run on the **worker** (not synchronously in the request handler), with the file written to **Supabase Storage**. *(BILL-007, §11.7, §15.10, STACK §3.11/§3.12, §20.4)*
- **FR-021**: Every export MUST create a durable **Export Batch** record (customer, period, format, file location, generated-by, generated-at, trip count, **totals** — the summed final billable value of the included trips in the period currency — and status) — mirroring slice 004's Import Batch — and the Billing screen MUST show **export-batch history**. A failed export MUST record a useful error on the batch and MUST NOT leave trips half-transitioned. *(BILL-008, §15.10, STACK §3.11)*

- **FR-023**: When the exact **finance export format** is **not yet supplied**, the export MUST use a **labeled default column set** and report **export sign-off as blocked** until the format is provided. *(§29 Input #4; Constitution II)*

**Worker jobs & §17 alerts (§17 cases 7–8, §15.2, §15.4; reuses 007)**

### Key Entities *(six §14.1 entities → seven `0007` tables — the Billing Item is realized as `billing_items` + a `billing_adjustments` line table per the plan; `trip_status`/`billingStatus` projection, the 007 `alerts` store, and Supabase Storage reused)*

- **Document** *(NEW; PRD §14.1, §13.9)*: a proof-of-execution file attached to a trip — trip reference; **document type**; **file location** (Supabase Storage object key — binary never in Postgres); **external reference** (CT-e / MDF-e / POD / gate receipt / customer-portal); **uploaded-by**; **upload timestamp**; **verification status** (accepted / rejected / pending review — default pending review); **verified-by**; **verified timestamp**; **notes**; **active/archived** (soft-delete). Drives completion/billing gating and the missing-document lists/alerts.
- **Document Requirement** *(NEW — customer config; PRD §14.1, CUST-004, DOC-003)*: a per-customer required-document checklist entry — customer reference; **document type**; **required-for-completion** (blocks Completed); **required-for-billing** (blocks Billing Ready); optional **scope** (lane / vehicle type); **active** flag. One config-driven engine, not per-customer code. Absence ⇒ default checklist + sign-off blocked. A required type is satisfied by an **accepted document** or an **audited "unavailable-with-reason" waiver** (who/when/why) — modeled at plan time as a waiver record or an "unavailable" document state, the spec fixes the behavior not the table shape.
- **Document Type** *(NEW — configurable admin-managed master; PRD §13.9, §14.1; mirrors 007 `reason_codes`)*: the proof-document vocabulary — **code**, **label** (pt-BR), **active** flag; seeded with defaults (POD, CT-e, MDF-e, gate receipt, customer-portal reference) and extensible **without code changes**. Referenced by Document Requirements and Documents; administered via `manage_commercial_data`.
- **Rate** *(NEW; PRD §14.1, BILL-002)*: a simple rate — customer reference; **lane**; **vehicle type**; **effective start/end**; **base amount** (integer minor units); **currency** (BRL default); optional **toll / waiting-time / extra-stop handling rules**; **active** flag. Most-specific currently-effective rate is applied; absence ⇒ manual amount + sign-off blocked.
- **Billing Item** *(NEW; PRD §14.1, BILL-001..006)*: the per-trip financial record — trip reference; customer; **base freight amount** (executed value — from rate or manual); typed **adjustments** (toll / waiting_time / redelivery / extra_stop / penalty / discount / manual_adjustment — each amount + note; persisted as a sibling **`billing_adjustments`** line table at plan time); **currency**; computed **planned / executed / adjustment / final billable** values; **billing period** (defaults to the calendar month of completion, editable); **dispute status** (gates Billing Ready; full dispute workflow owned elsewhere); **export-batch reference**; **notes**. Carries money + linkage, **not** a status machine — billing lifecycle status is 003's `billingStatus(current_status)` projection.
- **Export Batch** *(NEW; supports BILL-008 — mirrors slice 004's Import Batch)*: a durable record of one export run — customer; **billing period**; **format** (CSV / XLSX); **file location** (Supabase Storage); **generated-by**; **generated-at**; **trip count**; **totals** (summed final billable value, period currency); **status** (queued / running / completed / failed) + error message on failure. Billing Items link to it via export-batch reference; provides BILL-008 export history.
- **Trip billing/completion lifecycle** *(REUSED — owned by slice 003)*: Completed / Billing Pending / Billing Ready / Billed are **values of the single `trip_status` enum**, reached via 003's `transitionTripStatus` service; **billing status is the `billingStatus(current_status)` projection** over the four-member billing-phase domain `{billing_pending, billing_ready, billed, disputed}`, not a new field. This slice writes the transitions (gated + audited) but does not own or redefine the machine.
- **In-app Alert** *(REUSED — owned by slice 007)*: the `alerts` store and idempotent per-(trip, case) generation/auto-resolve framework; this slice supplies the inputs for the two previously-deferred §17 cases (7 — completed-but-missing-documents; 8 — billing-blocked-by-missing-proof). Not an external-channel notification.

## Scope

### In scope

- **Documents**: upload, type, external reference, notes, **verification** (accepted/rejected/pending review), download, and the **missing-document list** — the Documents screen + Trip-Detail documents section (filling slice 005's placeholder). *(DOC-001..006, §15.9)*
- **Per-customer required-document checklists** (CUST-004, DOC-003) driving completion/billing blockers, reusing `manage_commercial_data`.
- **Completion** (§19.3) and **Billing Ready** (§19.4) **gating**, enforced as 003 status-machine transitions (`mark_completed` / `mark_billing_ready`), with configurable block-vs-warn + audited per-document unavailable-with-reason waiver.
- **Simple rates** (BILL-002/003) and per-trip **billing computation** with typed adjustments and the planned/executed/adjustment/final breakdown (BILL-004/005); the Billing screen (billing-pending + billing-ready lists) + Trip-Detail billing section.
- **Billing export** to CSV/spreadsheet (BILL-007) on the worker, with durable **Export Batch** history (BILL-008) and configurable lock/flag (`billing_ready → billed`).
- Filling slice 005's reserved **documents/billing-detail** Trip-Detail placeholders, the Home Dashboard **"Completed trips missing documents"** widget, and the **"Missing documents"** board view (005's view framework); lighting up slice 007's two deferred **§17 alert cases** (7–8) via its existing alert framework.
- First enforcement of `upload_documents`, `verify_documents`, `mark_completed`, `mark_billing_ready`, `edit_rates`, `export_billing`; reuse of `manage_commercial_data` for document checklists.

### Out of scope (owned by later slices or post-MVP)

- **Mobile photo upload** (DOC-007, §20.3 Later) and **OCR / document data extraction** (DOC-008, §20.3 Later).
- **Customer-specific invoice layouts** (BILL-009, Later) and **ERP / accounting integration / invoice generation / AR sync** (BILL-010, §20.4 Later).
- An **advanced billing engine** beyond simple rates + manual adjustments (§24 mitigation — expand later).
- **External document storage / customer-portal document sync / CT-e·MDF-e provider integration** (§20.3 Later).
- **Per-customer SLA rules and SLA classification** (slice 007) and **SLA / billing-readiness *reporting* dashboards** (SLA-005, REP-002/003/004 — slice 009).
- The **"Billing pending count" dashboard widget and the billing-status board filter** — already **shipped live by 005** (the billing-phase statuses existed from 003); this slice does not re-home them.
- The full **dispute-resolution workflow** and the `disputed` status round-trip (owned by slice 003 / later); this slice only **reads** an open-billing-dispute flag as a Billing-Ready gate.
- **Back-filling 007 exception/event attachments** onto the new storage surface — enabled by this slice but not part of its acceptance bar.

## Assumptions

- **Status-machine reuse**: Completed / Billing Pending / Billing Ready / Billed are existing `trip_status` values reached through 003's `transitionTripStatus` service; billing status is 003's `billingStatus(current_status)` projection. This slice adds gating + monetary/document data, **not** a new lifecycle. *(003 data-model R2/R3)*
- **005 placeholder reuse**: the Trip-Detail documents/billing-detail sections, the "Missing documents" board view, and the "Completed trips missing documents" dashboard widget exist as 005 placeholders for this slice to fill; the **"Billing pending count" widget and billing-status filter already ship live in 005** (the billing-phase statuses existed from 003), so this slice does **not** re-home them. *(005 FR-017/FR-018/FR-029)*
- **007 alert reuse**: the in-app `alerts` store + idempotent generation/auto-resolve framework exists (007); this slice only **supplies the inputs** for the two deferred §17 cases — it does not build a new alert system, and adds no external channel. *(007)*
- **Storage surface**: Supabase Storage is the binary store (STACK §3.9); this slice introduces the document/export buckets whose absence caused 007 to defer attachments. Attachment back-fill for 007 is a non-blocking follow-on.
- **Required proof documents** are a gated business input (§29 Input #3): default = **configurable default checklist + document-checklist sign-off blocked** per customer until supplied — configurable, not invented. *(Constitution II)*
- **Finance export format** is a gated business input (§29 Input #4): default = **labeled default column set + export sign-off blocked** until the exact layout is supplied. *(Constitution II)*
- **Billing rules** (toll/waiting-time/penalty/cancellation handling) are a gated business input (§29 Input #5): default = **manual values/adjustments + billing-rule sign-off blocked** per customer until supplied. *(Constitution II)*
- **Block-vs-warn** for missing documents is per-customer/company policy with a **default of block**; a required document is satisfied by an accepted upload or an audited **per-document unavailable-with-reason waiver** (mirrors 006's configurable blocking-vs-warning). *(DOC-005, BILL-006, §11.6)*
- **Monetary model**: integer minor units + currency code, **BRL** default (§14 conventions); no multi-currency conversion in MVP.
- **Export lock/flag**: default = transition exported trips to `billed` (lock); flag-only is a config alternative (§11.7 step 7).
- **Worker & queue**: billing export (on-demand) and missing-document checks (periodic, ~5-min default) run on the **single Node worker + `pg-boss`** — no Redis/BullMQ, no Edge Functions, no new worker process. *(STACK §3.11)*
- **Billing Item decomposition**: whether typed adjustments are columns or a child line table is a planning decision; the spec fixes only the breakdown behavior (BILL-004/005).

## Blocked / Open for business sign-off

Design decisions are resolved as informed defaults in **Clarifications**; the items below are **business-input or later-slice gaps**, each with an explicit default so the slice ships and is not blocked from building.

1. **Per-customer required proof documents** *(PRD §29 Input #3; CUST-004, DOC-003/005, BILL-006, §19.4)* — **Open (business input).** Until Customers/Ops supply each customer's required-document list, the system runs on a **configurable default checklist** and each affected customer is reported **document-checklist sign-off blocked**. Not a build blocker.
2. **Finance billing export format (exact columns / layout)** *(PRD §29 Input #4; BILL-007/008, §11.7)* — **Open (business input).** Export uses a **labeled default column set**; export sign-off reported **blocked** until Finance supplies the exact layout. Not a build blocker.
3. **Per-customer billing rules (toll / waiting-time / penalty / cancellation handling)** *(PRD §29 Input #5; BILL-004, §19.5)* — **Open (business input).** Billing accepts **manual values/adjustments**; billing-rule sign-off reported **blocked** until Finance supplies the rules. Not a build blocker.
4. **Block-vs-warn document policy** *(DOC-005, BILL-006; §19.4, §11.6)* — **Resolved default.** Default = **block**; a required document is satisfied by an accepted upload or an audited **per-document unavailable-with-reason waiver**; per-customer/company policy can switch block→warn. Configurable, not invented.
5. **Export lock vs flag** *(§11.7 step 7)* — **Resolved default.** Default = transition exported trips to **`billed`** (lock); flag-only is a configuration alternative.
6. **007 exception/event attachment back-fill** *(007 deferral; STACK §3.9)* — **Deferred (enabled, not in this acceptance bar).** This slice's storage surface makes the deferred 007 attachments buildable; wiring them onto existing exceptions/events is a non-blocking follow-on.
7. **Full dispute-resolution workflow** *(§19.4, §19.5; `disputed` status)* — **Deferred.** This slice reads an open-billing-dispute flag as a Billing-Ready gate only; the `disputed` round-trip and resolution UI are owned by 003 / later.
