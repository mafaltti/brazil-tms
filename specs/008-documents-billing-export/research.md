# Phase 0 — Research & Design Decisions: Documents, Completion, Billing Readiness, Rates, and Export

**Feature**: 008-documents-billing-export · **Date**: 2026-06-01 · **Spec**: [spec.md](./spec.md)

This slice has **no open NEEDS CLARIFICATION** — the spec's two `/speckit-clarify` sessions (2026-05-31 design defaults, 2026-06-01 pre-plan) resolved every decision that changes data model, scope, or tests: completion/Billing-Ready are transitions on the **existing 003 status machine** (billing status is the `billingStatus(current_status)` **projection**, not a new column); a missing required document is satisfied by an **accepted upload or an audited per-document "unavailable-with-reason" waiver**; the billable breakdown is **typed adjustments** (amount + note); the **billing period defaults to the calendar month of completion** (editable); document **types are a configurable master list**; uploads are restricted to **PDF/JPG/PNG ≤ ~10 MB** (configurable). Remaining open items are gated business inputs (§29 Input #3 per-customer required documents, #4 finance export format, #5 per-customer billing rules) — scaffolded as **documented defaults + blocked sign-off, never invented** (Constitution II). The decisions below pin the technical approach against the **actual current codebase** (001 auth/audit/i18n/Storage-client, 002 master data + `manage_commercial_data`, 003 trip domain/`transitionTripStatus`/`billingStatus` projection/append-only logs, 004 import-batch + worker/pg-boss + `packages/db/src/storage.ts`, 005 read models + UI shell + dashboard + view registry, 007 `alerts` store + idempotent generation + first scheduled worker job).

---

## R0 — Reuse vs build: what 008 adds

**Decision**: 008 introduces **seven new tables** (`document_types`, `documents`, `document_requirements`, `rates`, `billing_items`, `billing_adjustments`, `export_batches`), **three new Postgres enums** (`document_verification_status`, `export_batch_status`, `billing_adjustment_type`), **two new pure domain modules** in `@brazil-tms/shared` (`domain/documents.ts` — verification vocab + checklist evaluation; `domain/billing.ts` — adjustment/format/export-status vocab + `computeBillingValues` + the two pure gate evaluators `evaluateCompletionReadiness` / `evaluateBillingReadiness`), **new Zod schema files**, **new service functions + read-model extensions** in `@brazil-tms/db`, **two new Storage buckets** (`documents`, `billing-exports`) + helpers in `packages/db/src/storage.ts`, **two new worker jobs** on the existing pg-boss queue (an **on-demand `billing.export`** job + a **scheduled `documents.checks`** sweep), **~18 BFF endpoints**, and the UI fills (Documents screen, Billing screen, Trip-Detail documents/billing sections, rate admin, document-requirement/document-type admin, the "Missing documents" board view, the "Completed trips missing documents" dashboard fill). It adds **no new permission key**, **no new package**, **no new worker process**, **no new runtime dependency**, and crucially **no `trips` ALTER** — billing status is the `billingStatus(current_status)` projection 003 already defines, so no document/rate/billing columns land on `trips` (the tables FK *to* `trips`).

**Rationale**: CUST-004 + DOC-001..006 + BILL-001..008 + the PRD §14.1 Document / Document Requirement / Rate / Billing Item / Export Batch entities are exactly slice 008's ownership (`docs/SPEC-SLICING.md`). Everything else — the `trip_status` machine, `transitionTripStatus` (which already records `trip_events` + audit + an in-tx `recomputeTripSla`), the `billingStatus` projection, `customers`/`lanes`/`vehicleType`, `manage_commercial_data`, the append-only `audit_logs`, the 005 board/detail/dashboard read models + view registry, the 007 `alerts` store + idempotent generation, the 004 worker + pg-boss + `packages/db/src/storage.ts` Supabase Storage client — already exists and is reused read-only or extended in place (Constitution I DRY/YAGNI, III single source). Three enums are created (vs CHECK text) because verification status, export-batch status, and adjustment type are **hard fixed domain sets referenced by service/gating/computation logic** — the codebase convention (`enums.ts` `pgEnum` for fixed logic-referenced sets; `text + CHECK` for business-mutable value sets like `reason_codes.category`). `export_batch_status` mirrors the existing `import_batch_status` pgEnum exactly. **Document `type` is a configurable master *table* (`document_types`), not an enum** (clarify Q2 — config-driven variation, Constitution V; mirrors `reason_codes`); **export `format` is `text + CHECK ('csv','xlsx')`** (a 2-value display set, no logic branch worth an enum); **`rates.currency` is `text` default `'BRL'`** (no multi-currency in MVP).

**Alternatives rejected**: a `manage_documents` / `configure_billing` permission key (the matrix has none — the spec reuses the six pre-declared keys + `manage_commercial_data`); a `document_type` enum (clarify Q2 chose a configurable master table); **aggregate adjustment columns** on `billing_items` (PRD §14.1 lists Tolls/Extras/Penalties/Discounts as fields, but spec FR-016 requires **each typed adjustment to carry an amount + note** and BILL-004 enumerates seven *addable* types — aggregate columns cannot hold per-entry notes or multiple entries of one type, so a child `billing_adjustments` line table is the **simplest model that satisfies the requirement**, R6); a `trips` ALTER adding billing/document columns (the 003 comment reserved them, but the projection + FK-to-trips design needs none — YAGNI); a new worker process or a second queue (Constitution — one app + one worker; pg-boss already committed); a CSV/XLSX dependency (ExcelJS — already a worker dep — emits **both** via `.xlsx.writeBuffer()` and `.csv.writeBuffer()`, so no `csv-stringify`).

## R1 — `document_types` master + `documents` table (clarify Q2; DOC-001/002/004/006)

**Decision**: A configurable master table **`document_types`** (`id`, `code` text unique, `label_pt` text, `active` boolean, `sort_order`, timestamps) — mirroring `reason_codes` — referenced by both `documents` and `document_requirements` via `document_type_id` FK; seeded (labeled scaffolding) with **POD, CT-e, MDF-e, gate receipt, customer-portal reference**, extensible without a code change (Constitution V). The **`documents`** table (PRD §14.1): `id`, `trip_id` FK→trips (not null), `document_type_id` FK→document_types (not null), `file_storage_key` text (**nullable** — a waiver row has no file), `external_reference` text (CT-e/MDF-e/POD/gate-receipt/portal), `uploaded_by_user_id` FK→users (not null), `verification_status` (`document_verification_status` enum, not null default `'pending_review'`), `verified_by_user_id` FK→users (nullable), `verified_at` timestamptz (nullable), **waiver columns** `waived_at` timestamptz (nullable) / `waived_reason` text (nullable) / `waived_by_user_id` FK→users (nullable) (R3), `notes` text, `archived_at` timestamptz (nullable — soft-delete), `created_at`/`updated_at`. A CHECK `documents_file_or_waiver_ck` enforces **`file_storage_key IS NOT NULL OR waived_at IS NOT NULL`** (a row is either an uploaded proof or a waiver, never neither). Binaries live in **Supabase Storage** (R8); only the `file_storage_key` lives in Postgres (STACK §3.9). Full DDL in [data-model.md](./data-model.md).

**Rationale**: 1:1 with PRD §14.1's Document fields. `document_type_id` references the clarify-Q2 master so checklists and uploads share the same vocabulary and new proof types need no migration. **`verification_status` is a pgEnum** (`accepted`/`rejected`/`pending_review`) — a fixed set the completion/billing gate logic branches on (the enum-vs-CHECK convention; mirrors `exception_status`). `archived_at` soft-delete matches the master-data convention (RECON: `customers`/`lanes`/`drivers` use a nullable `archived_at`, not an `active` boolean) and Constitution III (never hard-delete auditable records). Indexes: `documents_trip_idx (trip_id)`, `documents_type_idx (document_type_id)`, `documents_verification_idx (verification_status)`.

**Alternatives rejected**: a `document_type` enum (Q2 — config table); storing the binary in Postgres (STACK §3.9 forbids); an `active` boolean instead of `archived_at` (the codebase soft-delete convention is `archived_at`); a separate `document_waivers` table (R3 — folded into `documents` as a waiver row, keeps requirement-satisfaction a single-table query).

## R2 — `document_requirements` checklist + default checklist (CUST-004, DOC-003/005)

**Decision**: A per-customer config table **`document_requirements`**: `id`, `customer_id` FK→customers (not null), `document_type_id` FK→document_types (not null), `required_for_completion` boolean not null default false, `required_for_billing` boolean not null default true, optional scope `lane_id` FK→lanes (nullable) / `vehicle_type` (`vehicle_type` enum, nullable), `active` boolean not null default true, timestamps. **Applicability**: a requirement applies to a trip when `customer_id` matches AND (`lane_id` IS NULL OR = trip.lane_id) AND (`vehicle_type` IS NULL OR = trip.planned_vehicle_type) AND `active` — i.e. unscoped rows apply to all the customer's trips and scoped rows **add** when the trip matches (additive, the spec's "in addition to/over" reading). **Absence of any rows for a customer ⇒ the labeled-configurable `DEFAULT_DOCUMENT_CHECKLIST` applies AND that customer's document-checklist sign-off is reported blocked** (FR-013, §29 Input #3). Indexes: `document_requirements_customer_idx (customer_id)`, `document_requirements_scope_idx (customer_id, lane_id, vehicle_type)`.

**Rationale**: matches PRD §14.1's Document Requirement entity and CUST-004 exactly; per-customer commercial config administered via the reused `manage_commercial_data` key (R12, mirroring 007's SLA-rule reuse). `DEFAULT_DOCUMENT_CHECKLIST` is a constant in `@brazil-tms/shared` (mirrors 007's `DEFAULT_SLA_POLICY`) — e.g. `[{ typeCode: 'pod', requiredForBilling: true }]` — labeled scaffolding, not invented sign-off (Constitution II). Additive scoping (not replace) is the natural reading and avoids a precedence ordering for what is a *set* of required types.

**Alternatives rejected**: a JSON checklist blob on `customers` (opaque, un-joinable, harder to scope/validate — explicit rows are queryable and Zod-checkable); replace-semantics for scoped rows (the spec edge case says scoped requirements apply *in addition to* the customer default — additive is correct); a DB row for the default checklist (a `@brazil-tms/shared` constant is the seam, like `DEFAULT_SLA_POLICY`, so "no customer rows" is unambiguous).

## R3 — Missing-document waiver: per-document "unavailable with reason" inside the gated transition (clarify Q3; FR-010, §11.6/§19.4)

**Decision**: A required document that genuinely cannot be provided is satisfied by an **audited per-document waiver** — a `documents` row with `file_storage_key = NULL` and `waived_at`/`waived_reason`/`waived_by_user_id` set. A requirement of type *T* is **satisfied** for a trip iff ∃ a non-archived `documents` row `(trip, T)` with `verification_status = 'accepted'` **OR** `waived_at IS NOT NULL`. The waiver is **recorded as part of the gated transition**, not via a standalone endpoint: `markCompleted` / `markBillingReady` accept an optional `waivedRequirements: [{ documentTypeId, reason }]` array; each waiver is inserted (a `documents` waiver row) inside the same transaction and audited as `document.waive`, **gated by the same transition key** (`mark_completed` / `mark_billing_ready`) the caller already holds. The gate still checks the **remaining** unwaived requirements.

**Rationale**: encodes clarify Q3 (per-document "unavailable with reason", not a blanket bypass) and FR-010 ("a gate-key holder records the specific required document as unavailable with a reason") **precisely** — binding the waiver to the gated transition (a) ties waiver authority to the gate key without the awkwardness of a standalone waiver endpoint needing both `mark_completed` and `mark_billing_ready`, (b) makes the waiver atomic with the transition, and (c) keeps it audited per-document (`document.waive`). Folding the waiver into the `documents` table (nullable file + waiver columns + the `file_or_waiver` CHECK) avoids an 8th table while keeping requirement-satisfaction a single-table query (R1).

**Alternatives rejected**: a standalone `POST /api/.../document-waivers` endpoint (auth ambiguity — a type can be both completion- and billing-required, so which gate key? — and a non-atomic waiver); a separate `document_waivers` table (an extra table for what is naturally a no-file document record); a 4th `verification_status` value `waived` (conflates file-review status with a no-file waiver — the waiver is orthogonal to verification).

## R4 — `rates` table + single-applicable-rate precedence (BILL-002/003)

**Decision**: A **`rates`** table: `id`, `customer_id` FK→customers (not null), `lane_id` FK→lanes (nullable scope), `vehicle_type` (`vehicle_type` enum, nullable scope), `base_amount_cents` bigint not null, `currency` text not null default `'BRL'`, optional `toll_handling_rule` / `waiting_time_rule` / `extra_stop_rule` text (nullable — labeled gated business inputs, §29 Input #5), `effective_start` timestamptz (nullable), `effective_end` timestamptz (nullable), `active` boolean not null default true, timestamps. **Single-applicable-rate precedence is resolved in the resolver's query** (mirroring 007's `customer_sla_rules` R3), NOT a DB constraint: `WHERE customer_id = ? AND active AND (effective window covers the trip's pickup) AND (lane_id = trip.lane_id OR lane_id IS NULL) AND (vehicle_type = trip.planned_vehicle_type OR vehicle_type IS NULL) ORDER BY (lane_id IS NOT NULL) DESC, (vehicle_type IS NOT NULL) DESC, effective_start DESC NULLS LAST LIMIT 1`. **No match ⇒ planned freight is left for a manual billing amount, and billing-rule sign-off is reported blocked** (§29 Input #5, FR-018). Indexes: `rates_customer_idx`, `rates_scope_idx (customer_id, lane_id, vehicle_type)`.

**Rationale**: matches PRD §14.1's Rate entity and BILL-002/003. Money is **`bigint` cents, `'BRL'`** per the codebase convention (RECON: `lanes.standard_rate_cents`/`toll_estimate_cents` are `bigint('…', { mode: 'number' })`). Precedence **lane+vehicle-type > single-scope > customer-default, tie-break latest `effective_start`** is the spec edge case, resolved in the query `ORDER BY … LIMIT 1` (not a `btree_gist` exclusion constraint — gated, low-volume, human-administered data; YAGNI, exactly the R3 reasoning). The toll/waiting-time/extra-stop *rules* are **nullable text** placeholders that are not interpreted in MVP (manual values until §29 Input #5 lands — never invented).

**Alternatives rejected**: a DB exclusion constraint on overlap (YAGNI — precedence handles it); interpreting toll/waiting/extra-stop rules now (gated Input #5 — manual values only, R6); a non-cents money type (the codebase stores integer cents).

## R5 — `billing_items` (BILL-001/003/005) — money + linkage, status is the projection

**Decision**: A **`billing_items`** table (one per trip, created at billing-phase entry — R7): `id`, `trip_id` FK→trips (not null, **unique** — one billing item per trip), `customer_id` FK→customers (not null), `base_freight_cents` bigint (nullable — rate-derived or manual; the **executed value** per spec FR-017), `rate_id` FK→rates (nullable — the rate applied, or null for a manual amount), `currency` text not null default `'BRL'`, `billing_period` text not null (the `YYYY-MM` of completion — R9), `dispute_status` text not null default `'none'` (CHECK `('none','open','resolved')`), `notes` text, `created_at`/`updated_at`. Computed values (**planned / executed / adjustment / final billable**) are **derived** in the read/service layer via `computeBillingValues` (R6) from `base_freight_cents` + the `billing_adjustments` rows — **not stored** (no drift; a recompute is cheap). **Billing lifecycle status is the `billingStatus(current_status)` projection** (003 R3, over `{billing_pending, billing_ready, billed, disputed}`) — `billing_items` carries **no status column** (FR-011). Index: `billing_items_trip_uq (trip_id)` unique, `billing_items_customer_period_idx (customer_id, billing_period)`, `billing_items_export_batch_idx`.

**Rationale**: matches PRD §14.1's Billing Item minus the redundant status (003 R3 projection is the single source — Constitution III, FR-011) and minus stored aggregate columns (derived from the line table — no drift). One-per-trip (unique `trip_id`) since a trip has one billing record. `billing_period text 'YYYY-MM'` default = month of completion (clarify Q1). `dispute_status` is the open-billing-dispute flag the §19.4 Billing-Ready gate reads (the full dispute workflow + the `disputed` status round-trip stay owned by 003/later — spec scope).

**Alternatives rejected**: storing computed planned/executed/adjustment/final columns (drift risk vs the adjustment lines — derive instead, Constitution III); a `billing_status` column (FR-011 — it is the 003 projection); a billing item per adjustment (the billing item is per-trip; adjustments are its lines — R6).

## R6 — `billing_adjustments` child line table + `computeBillingValues` (BILL-004/005, FR-016/017)

**Decision**: A child **`billing_adjustments`** table: `id`, `billing_item_id` FK→billing_items (not null), `type` (`billing_adjustment_type` enum — `toll`, `waiting_time`, `redelivery`, `extra_stop`, `penalty`, `discount`, `manual_adjustment`), `amount_cents` bigint not null (the user-entered signed value), `note` text (nullable), `created_by_user_id` FK→users (not null), `created_at`. A pure `computeBillingValues(baseFreightCents, adjustments)` in `@brazil-tms/shared/domain/billing.ts` returns `{ plannedCents, executedCents, adjustmentCents, finalBillableCents }`: **planned** = the matching rate's base (null if no rate), **executed** = `base_freight_cents` (rate-derived or manual — FR-017), **adjustment** = `Σ amount_cents` over the lines (discounts entered as negative, or `discount`-typed and subtracted — see below), **final billable** = `executed + tolls + extras + penalties − discounts ± manual_adjustment`. Sign convention: `discount` amounts are stored as positive and **subtracted** by the formula; all other types are **added**; `manual_adjustment` may be signed.

**Rationale**: spec FR-016 requires **each** typed adjustment to carry an amount **+ note**, and BILL-004 enumerates **seven addable types** — a child line table is the **simplest model that satisfies** itemized add + per-entry note + per-entry audit (aggregate columns on `billing_items` cannot hold a note or multiple entries of one type). `billing_adjustment_type` is a **pgEnum** (fixed set the computation branches on — the discount-subtraction rule). The value breakdown (FR-017/BILL-005) is **computed**, not stored (R5). The formula is the definitional composition of PRD §14.1's Billing Item fields (Constitution II — definitional, not invented; the per-customer charge *math* for tolls/penalties stays the gated §29 Input #5, manual until supplied).

**Alternatives rejected**: aggregate `tolls_cents/extras_cents/penalties_cents/discounts_cents` columns (cannot itemize or annotate — fails FR-016's "each with a note"; PRD entity uses columns but the clarify deferred the decomposition and FR-016 forces line items); storing computed totals (drift — R5); a `billing_adjustment_type` CHECK text (the computation branches on type — pgEnum is the convention fit, like `exception_severity`).

## R7 — Completion → auto-advance to Billing Pending; Billing Item creation (FR-007/008, §11.6, §19.3)

**Decision**: `markCompleted(tripId, input, actorUserId)` in `packages/db/src/trips/completion.ts` (1) gathers the completion context (current status, the applicable required-for-completion document types and which are satisfied incl. any waivers in `input.waivedRequirements`, §19.3 operational closure), (2) calls the **pure `evaluateCompletionReadiness(ctx)`** (R10) — if blocked, `throw new Conflict('COMPLETION_BLOCKED', …)` (with the missing types as `findings`), (3) records any `waivedRequirements` as waiver rows + `document.waive` audit, (4) calls **`transitionTripStatus(tripId, { toStatus: 'completed', expectedFromStatus: 'unloaded' }, actor)`** (reused — its concurrency guard + `trip_events` + `trip.status_change` audit + in-tx `recomputeTripSla`), then (5) **immediately** `transitionTripStatus(tripId, { toStatus: 'billing_pending', expectedFromStatus: 'completed' }, actor)` (§11.6 step 6 auto-advance) and (6) `ensureBillingItem(tripId)` (insert the `billing_items` row with `billing_period` = `YYYY-MM` of the completion timestamp, `base_freight_cents` from the resolved rate or null). `markBillingReady(tripId, input, actor)` gathers the §19.4 context (billing-required docs satisfied, `base_freight_cents` present (rate or manual), `dispute_status <> 'open'`), calls **`evaluateBillingReadiness(ctx)`** — blocked ⇒ `Conflict('BILLING_READY_BLOCKED', …)` — then `transitionTripStatus(tripId, { toStatus: 'billing_ready', expectedFromStatus: 'billing_pending' }, actor)`.

**Rationale**: completion/Billing-Ready are **status transitions on the existing 003 machine** (clarify; FR-007/009) — the status change MUST go through `transitionTripStatus` (the authority that guards concurrency, writes `trip_events` + audit, and recomputes SLA), never a re-implemented machine (Constitution III, DRY). The gate is enforced **before** the transition (a refused completion changes no state). The §11.6 auto-advance (completed→billing_pending) is a second `transitionTripStatus` call; if it fails the trip rests at `completed` (a legal state), so the sequence is safe. `ensureBillingItem` at billing-phase entry gives finance a record to price (FR-008).

**Alternatives rejected**: a new completion/billing status machine (FR-007/009/011 — reuse 003); gating inside `transitionTripStatus` (it is generic across all transitions — the 008-specific document/pricing gate belongs in the `markCompleted`/`markBillingReady` wrappers, not the shared service); creating the billing item lazily at Billing-Ready (finance needs to price during Billing Pending — create at billing-phase entry).

## R8 — Supabase Storage: `documents` + `billing-exports` buckets, helpers in `packages/db/src/storage.ts` (DOC-001, BILL-007, STACK §3.9)

**Decision**: Extend the existing **`packages/db/src/storage.ts`** (the service-role Storage client reused by the Next app **and** the worker — RECON) with: `documentsBucket()` (env `DOCUMENTS_BUCKET ?? 'documents'`), `exportsBucket()` (env `EXPORTS_BUCKET ?? 'billing-exports'`), `documentStorageKey(tripId, documentId, ext)` (→ `trips/${tripId}/${documentId}.${ext}`), `exportStorageKey(exportBatchId, ext)` (→ `exports/${exportBatchId}.${ext}`), `putDocument(key, bytes, contentType)`, `putExport(key, bytes, contentType)`; **reuse** the existing `downloadObject(key)` and `signedUrl(key, expiresInSeconds)`. The BFF re-export `apps/web/lib/supabase/storage.ts` (the `server-only` boundary) re-exports the new helpers. **Document download** is served as a short-lived **signed URL** (reusing `signedUrl`) returned by a BFF route gated on `view_all_trips` (FR-004) — the binary never streams through a public path and the service-role key never leaves the server. Buckets are provisioned the same way as `imports` (an idempotent `createBucket` at setup / a documented setup step). New env vars: `DOCUMENTS_BUCKET`, `EXPORTS_BUCKET`, `DOCUMENT_MAX_BYTES` (R9), `DOCUMENT_CHECKS_CRON` (R11) — added to `apps/web/.env.local.example`, `workers/.env`, and the docker-compose worker env (mirroring `IMPORT_BUCKET`/`SLA_SWEEP_CRON`).

**Rationale**: 008 is the **first feature to store its own binaries** beyond 004's import files; `packages/db/src/storage.ts` already encapsulates the service-role Supabase Storage client (used by both app and worker), so 008 **adds helpers** rather than a new client (DRY, Constitution I/IV — the service-role key stays server-only). Signed-URL download keeps Constitution IV (no public binary path, key server-only) and satisfies "document access follows trip/customer permissions" (FR-004 — gated by the same `view_all_trips` read the trip uses; per-customer scoping arrives with Customer Viewer post-MVP). This is the surface whose absence made 007 defer attachments (spec dependency).

**Alternatives rejected**: a second Storage client (the shared `getClient()` already serves app + worker — DRY); streaming binaries through the BFF (signed URLs are simpler and offload bytes to Storage); a public bucket (Constitution IV — access must follow permissions); storing in Postgres (STACK §3.9 forbids).

## R9 — Upload validation + billing period (clarify Q1/Q4; FR-001)

**Decision**: The upload BFF route validates the file **before** Storage: allowed types from a configurable list **default PDF/JPG/PNG** (by extension + content-type), max size from `DOCUMENT_MAX_BYTES` **default ~10 MB** (`10 * 1024 * 1024`); a disallowed type ⇒ `409 UNSUPPORTED_FILE_TYPE`, oversize ⇒ `409 FILE_TOO_LARGE` (mirroring 004's `inferFileType`/`UNSUPPORTED_FILE_TYPE` extension check), and **nothing is stored**. Uploads use `multipart/form-data` (a `File` → `Buffer.from(await file.arrayBuffer())`, the 004 pattern). **Billing period** is `text 'YYYY-MM'` set by `markCompleted` to the calendar month of the completion timestamp in **`America/Sao_Paulo`** (Luxon `DateTime.fromJSDate(ts, { zone })`.`toFormat('yyyy-MM')`), editable by finance via the billing PATCH; the Billing screen + export filter by `customer_id` + `billing_period`.

**Rationale**: encodes clarify Q4 (PDF/JPG/PNG ≤ ~10 MB, both configurable) and Q1 (period = month of completion, editable). Validating in the BFF (not only the Storage 50 MB container limit) makes FR-001's "rejected with a clear message, nothing stored" testable and is the security posture the spec chose. Month boundary in `America/Sao_Paulo` matches the canonical business timezone (a trip completed at 23:00 UTC on the 31st belongs to the right local month). Both limits are **configurable, not gated business inputs** (clarify Q4).

**Alternatives rejected**: relying solely on the Storage container `FILE_SIZE_LIMIT` (no clear BFF message, no type allow-list — fails FR-001); a free date range at export (clarify Q1 chose month-of-completion); computing the month in UTC (could mis-bucket month-boundary completions).

## R10 — Completion + Billing-Ready gates: pure evaluators in `shared` (FR-007/009/013, §19.3/§19.4)

**Decision**: Two pure, DB-free functions in `@brazil-tms/shared/domain/billing.ts` (the BFF/service gathers the context; the UI never decides — STACK §3.13 names **billing-readiness rules** a required Vitest focus, exactly like the SLA evaluator):
```ts
evaluateCompletionReadiness(ctx): { canComplete: boolean; blockers: CompletionBlocker[] }
evaluateBillingReadiness(ctx): { canBillReady: boolean; blockers: BillingBlocker[] }
```
`CompletionBlocker` ∈ `not_unloaded | missing_completion_documents | cancelled`; `BillingBlocker` ∈ `not_billing_pending | missing_billing_documents | no_pricing | open_billing_dispute`. The completion ctx carries `currentStatus`, the applicable **required-for-completion** type ids + which are satisfied (accepted-or-waived). The billing ctx carries `currentStatus`, the **required-for-billing** type ids + satisfied set, `hasPricing` (`base_freight_cents != null`), `disputeStatus`. `evaluateChecklist(requiredTypes, satisfiedTypeIds)` in `domain/documents.ts` returns the unmet completion/billing type sets. Block-vs-warn is a config flag the caller applies (default **block** — clarify), but the evaluator always **reports** blockers (never silently passes).

**Rationale**: STACK §3.13 lists "billing-readiness rules" as a Vitest focus → a pure function is unit-testable without a DB (mirrors 007's `evaluateSlaRisk`). Authority is server-side (Constitution III, FR-007/009) — the gate result drives the `Conflict` the BFF returns; the UI only *renders* the blockers it gets back. Encodes §19.3 (milestones/closure + completion docs) and §19.4 (completed + billing docs + pricing + dispute) verbatim.

**Alternatives rejected**: gating in SQL/the route handler (un-unit-testable; duplicated logic — DRY); a single combined gate (completion and Billing-Ready are distinct transitions with distinct rules — two evaluators).

## R11 — Worker: `billing.export` (on-demand) + `documents.checks` (scheduled) on the existing pg-boss + single worker (BILL-007/008, §17 cases 7–8)

**Decision**: The **single existing `@brazil-tms/workers` process** gains **two jobs** (no new process/queue): **(a) `billing.export`** — *on-demand*, enqueued by the BFF (`boss.send`) when finance triggers an export; `workers/jobs/billing-export/index.ts` exports `runBillingExport({ exportBatchId, actorUserId })` + `registerBillingExport(boss)` (mirrors the import-job `runXxx`/`registerXxx` + `setBatchStatus` durable-status pattern): set `running` → load the export batch's `customer_id`+`billing_period` → select the **billing-ready** trips + their computed billing values → generate the file (**ExcelJS**: `.xlsx.writeBuffer()` or `.csv.writeBuffer()` per `format` — no new dep) → `putExport(key, bytes, …)` → set `file_storage_key`, `trip_count`, `total_amount_cents`, status `completed` → transition each included trip **`billing_ready → billed`** via `transitionTripStatus` (configurable lock/flag — default lock, R-config); a throw sets the batch `failed` + `error_message` (durable status, idempotent retry skips already-`billed` trips). **(b) `documents.checks`** — *scheduled* via `boss.schedule(JOB.documentChecks, cron, {}, {})` (cron `DOCUMENT_CHECKS_CRON` default `*/5 * * * *` — the **second** scheduled job, mirroring 007's `sla-sweep`); `runDocumentChecks()` sweeps **billing-phase trips** (`current_status ∈ {billing_pending, billing_ready}` — R-D from clarify CON-3), per-trip fault isolation (try/catch skip-and-continue), and **generates/auto-resolves the two §17 alerts on distinct per-case predicates** through the **007 `alerts` store**: **case 7 `completed_missing_documents`** fires when the trip has **≥1 unmet required document of any kind** (any non-archived required type lacking an accepted-or-waived document); **case 8 `billing_blocked_missing_proof`** fires **only** when `evaluateBillingReadiness` returns the **`missing_billing_documents`** blocker (a billing item that cannot reach Billing Ready *specifically* for missing required-for-billing proof — the spec's "once a Billing Item is blocked", FR-025/US2-AS5 — **not** merely `no_pricing`/`open_billing_dispute`). Each case is generated/auto-resolved **independently** — `INSERT … ON CONFLICT (alerts_trip_case_open_uq) DO NOTHING` per case to generate, conditional `UPDATE … state='resolved'` per case when that case's condition clears — and case 7 feeds the `completedMissingDocuments` dashboard metric. Job-name/payload contracts live in `@brazil-tms/shared` (`billing/jobs.ts` → `BILLING_JOBS = { billingExport: 'billing.export' }`; `documents/jobs.ts` → `DOCUMENT_JOBS = { documentChecks: 'documents.checks' }`), merged into `workers/lib/queue.ts` `JOB`/`JobPayloads`/`setupQueues`; the BFF enqueue client is `apps/web/lib/billing/queue.ts` (mirrors `apps/web/lib/imports/queue.ts`).

**Rationale**: STACK §3.11 + the constitution mandate the **Postgres-backed queue + one worker** — pg-boss is already committed and 004's import-batch + 007's scheduled-sweep patterns are the exact templates. Heavy export generation MUST run off the request path (STACK §3.11/§3.12, FR-019). The two deferred §17 cases (7, 8) are lit up by **feeding the 007 alert framework** (reuse, not a new alert system — FR-024/025). ExcelJS (already a worker dep) emits both CSV and XLSX → no new dependency.

**Alternatives rejected**: generating the export synchronously in the BFF (STACK §3.11/§3.12 — heavy work off the request path); a new worker process / queue (Constitution — one app + one worker); a CSV library (`csv-stringify`) (ExcelJS covers CSV — YAGNI); a new alert store (007's exists — reuse).

## R15 — Performance, freshness, scale (SC-010, FR-029/030)

**Decision**: Freshness = **polling** reusing 005's cadences — board `CONTROL_TOWER_POLL_MS = 30 s`, dashboard `DASHBOARD_POLL_MS = 60 s`, detail `TRIP_DETAIL_POLL_MS = 30 s` (RECON `apps/web/lib/trips/client.ts`); the Documents + Billing lists poll on the board cadence; new client hooks invalidate `["trips"]` (and new `["billing"]`/`["documents"]` roots) via the `useMutation` + `invalidateQueries` pattern. **No Realtime** (FR-030). Targets: the **pure gate evaluators** + `computeBillingValues` are sub-millisecond; Documents screen, the Billing pending/ready lists, and the Trip-Detail documents/billing sections load within **~3 s** at medium scale (the §21.2 trip-**list** bar — an intentional relaxation of the 2 s trip-**detail** bar for the new Storage/billing-backed sections), backed by the `documents_*`/`rates_*`/`billing_items_*`/`export_batches_*` indexes; a **billing export** over a customer+period batch (up to ~hundreds of trips) completes on the worker within a configurable soft target (~a few minutes) with a durable batch status; the `documents.checks` sweep over billing-phase trips (chunked, per-trip fault isolation) completes within its ~5-min cadence.

**Rationale**: medium scale inherited from 005/007; indexed reads + pure evaluators + a chunked sweep + off-request-path export keep every surface within target without Realtime (Constitution / STACK §3.10–§3.11). Polling reuse = zero new freshness mechanism.
