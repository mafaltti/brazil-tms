# Implementation Plan: Reporting, Audit Views, Hardening, and MVP Acceptance

**Branch**: `009-reporting-audit-hardening` | **Date**: 2026-06-01 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/009-reporting-audit-hardening/spec.md`

## Summary

This is the **performance-visibility, hardening, and MVP-acceptance close-out** — the final MVP slice. Business users (operations managers, finance analysts, executives) get a **Reports** screen (`Relatórios`) with the three MVP-acceptance reports — **SLA performance by customer/lane/period** (SLA-005, REP-002), **exception volume & delay reasons** (REP-003), and **billing readiness** (REP-004) — so the spreadsheet stops being the system of record (§22 Phase 5 exit criterion). The slice also fills the audit-history gap **where not already embedded** (§21.5/§13.12) and proves the cross-cutting quality bars for MVP acceptance (§23): permission coverage (§18/§21.4), audit completeness (§21.5), localization coverage (§21.6), and performance (§21.2), recorded in an end-to-end **traceability matrix** mapping every §23 criterion to its PRD requirement IDs and owning slice.

Technical approach: 009 is **read-only over existing data and adds no new durable state** — **no new table, enum, migration, permission key, package, worker job, or runtime dependency**. The three reports are **synchronous read-model projections** over data slices 003–008 already produce: `trips.sla_status`/`trips.sla_reasons` + `trip_events` (007), `exceptions` + `reason_codes` (007), the `billingStatus(current_status)` projection (003) + `billing_items.billing_period` (008). They live beside the established 005 read-model layer (`packages/db/src/trips/trips-read.ts`) as three new query functions (`querySlaReport` / `queryExceptionReport` / `queryBillingReadinessReport`) re-exported server-only via `apps/web/lib/trips/trips-read.ts`. Per clarify Q4 (**reuse 007's on-time definition exactly**), the on-time pickup/arrival **predicate** currently inlined in `queryDashboardMetrics` is **extracted once** into a shared SQL helper (`onTimeExpr`) consumed by **both** the dashboard metric and the SLA report — DRY-for-correctness so the two surfaces can never show divergent on-time numbers. The **audit-history view** is an **extension** of the already-shipped `GET /api/admin/audit-logs` endpoint and its `(shell)/admin/audit/` screen (slice 001, gated `view_audit_log`): 009 adds `actorUserId` + `from`/`to` date-range filters, pagination, and an actor-name/entity-label join, and widens the screen to the §21.5 record types (status / assignment / document-verification / billing / export-batch). Per clarify Q1 (**pass-with-blocked-sign-off**), the gated business inputs are **documented configurable defaults with the affected sign-off marked blocked, never invented** (Constitution II): per-customer SLA rules (§29 Input #2 — SLA report runs on `DEFAULT_SLA_POLICY`, SLA-reporting sign-off blocked) and per-customer document/billing rules (§29 Inputs #3/#4/#5 — billing-readiness report runs on the default checklist + manual values, billing-readiness-reporting sign-off blocked); each report renders a visible **provisional** banner until its inputs arrive. Authorization adds **no new key**: reports reuse **`view_all_trips`** (all seven internal roles, mirroring the 005 dashboard), the audit view reuses **`view_audit_log`** (Admin), and SLA-rule/document-requirement administration stays on **`manage_commercial_data`** (002). The **hardening + acceptance pillar** ships mainly as **tests + deliverable docs**: a Playwright permission-coverage suite (authorized 2xx vs unauthorized 403 for every operational/billing mutation across 001–008), an audit-completeness check (every §21.5 action type writes an append-only `audit_logs` row), an extended `messages.test.ts` localization guard, a performance validation against seeded volumes, and the MVP-acceptance traceability matrix. MVP reports are **tabular (TanStack Table) + summary cards** in pt-BR — **no charting library** is added (KISS / no new dependency); visualizations are a Later enhancement. Freshness is **polling via TanStack Query** (no Realtime).

## Technical Context

**Language/Version**: TypeScript 5.x (strict); Node.js 20 LTS; pnpm monorepo.

**Primary Dependencies** (existing — **no new runtime deps**): Next.js 15 (App Router) + React 19; Drizzle ORM over `postgres` (server-only, the read-model layer); Zod (report filter + audit-filter query validation, shared); Luxon (`America/Sao_Paulo` period/day-range derivation, reusing 005's `dayRangeSaoPaulo` and 008's month-of-completion billing-period convention); **TanStack Query** (polling reads) + **TanStack Table** (the report grids); `next-intl` (pt-BR — new `Reports`/`AuditView` namespaces); shadcn/ui + Radix + lucide-react (summary cards, filters, the `BarChart3` nav icon). **No charting library** (recharts/visx/etc.) — MVP reports are tables + summary number cards (KISS, Constitution I); charts deferred.

**Storage**: self-hosted Supabase Postgres — **read-only**. **Zero new tables, enums, or migrations**: every report is a projection over existing tables (`trips`, `trip_events`, `exceptions`, `reason_codes`, `customer_sla_rules`, `billing_items`, `audit_logs`). Existing indexes cover the rollups at MVP volume (§21.3 "thousands of trips per month" ⇒ a customer-month slice is hundreds of rows): `trips_customer_idx`, `trips_pickup_start_idx`, `trips_status_idx`; the fully-indexed `exceptions` (`_status_/_severity_/_reason_/_opened_idx`); `billing_items_customer_period_idx`; `audit_logs_{entity,actor,created}_idx`. **No speculative index is added** (YAGNI); candidate composite indexes (e.g. `trips(customer_id, planned_pickup_window_start)`) are listed in [research.md](./research.md) R6 as the *first* fallback **only if** a measured query misses the §21.2 budget — and would then be migration `0008` (next after `0007_nebulous_xorn.sql`). Service-role key server-only; gateway/PostgREST never exposed.

**Testing**: Vitest is the primary gate. **Pure unit** (`packages/shared`): the report filter Zod schemas (`reportFilterSchema`, the extended `auditLogQuerySchema`); the period/day-range derivation helper. **Service/integration** (`apps/web` lib, dev DB, `describe.skipIf(!DATABASE_URL)`, **static imports** per MEMORY): `querySlaReport` (on-time pickup/arrival % + on-track/at-risk/late/breached counts grouped by customer/lane/period; matches the dashboard's `onTimeExpr` on overlapping data — the single-source-of-truth assertion); `queryExceptionReport` (volume by reason-code category + severity, open/resolved, avg resolution time); `queryBillingReadinessReport` (phase counts via `billingStatus`, completed-missing-documents, %-ready-within-24h from `trip_events` completion→billing_ready gap); the extended `queryAuditLog` (actor + date-range filters, actor-name join). **Localization guard** (`apps/web/lib/messages.test.ts`, EXTEND): the new `Reports`/`AuditView` namespaces present and dot-free; the existing `ALL_AUDIT_ACTIONS`→flat-label invariant still holds. **Playwright** (`apps/web/e2e/`): the three report endpoints + the Reports screen (holder `200` vs non-holder of `view_all_trips` `403`); the audit-view filters + `view_audit_log` `403` for non-admin (extends `audit.spec.ts`); **`permission-coverage.spec.ts`** — the hardening matrix asserting authorized `2xx` vs unauthorized `403` for every operational/billing **mutation** endpoint across 001–008; **`audit-completeness.spec.ts`** — each §21.5 action type writes an `audit_logs` row. Route HTTP-status (401/403/400) + payloads asserted in `e2e/` (no `route.test.ts`, per MEMORY). MEMORY also applies: web vitest via `pnpm exec vitest run --project web <file>` with `DATABASE_URL`; e2e against a prod build, `--workers=1`, `db:seed:e2e` first.

**Target Platform**: Linux server via Docker Compose (Supabase, app, worker, Caddy). Desktop-first, evergreen browsers (PRD §16). **No worker change** — reports are computed **synchronously** in the BFF read path (small aggregates within the §21.2 budget); unlike 008's heavy export, no job is queued.

**Project Type**: Web application — existing monorepo (`apps/web` + `packages/{shared,db}` + `workers/`). **No new package, worker process, worker job, permission key, runtime dependency, table, enum, or migration.**

**Performance Goals**: each report (SLA / exception / billing-readiness) loads within **~3 s** for a single customer-month at representative daily volumes (the §21.2 trip-**list** bar; SC-002), served by existing indexes; the `onTimeExpr` predicate is evaluated in-SQL; the audit view is **date-range-scoped** so historical-across-years filtering (§21.3) stays in budget. Freshness = **polling** reusing 005's cadence (reports `60 s`, matching the dashboard); no Realtime.

**Constraints**: BFF-only authorization; **reports are read-only** — viewing never mutates state and **final SLA classification is never re-derived in the UI** (the report *displays* the stored `trips.sla_status`; Constitution III / STACK §6.1 "UI must not own final SLA classification"); audit history is **append-only** and the view never mutates or deletes it (Constitution III); soft-deleted/archived records are excluded from operational counts but retained in the audit view; service-role key server-only; gateway/PostgREST never public; **NO** Realtime / Edge Functions / Redis-BullMQ / microservices / route optimizer; freshness via **polling**; **reuses 001/003/005/007/008** read models, the `view_all_trips`/`view_audit_log`/`manage_commercial_data` keys, the append-only `audit_logs`/`trip_events`, and the i18n/nav/view registries **without redefining** them; UI pt-BR; timestamps UTC (displayed `America/Sao_Paulo`); money integer centavos (BRL).

**Scale/Scope**: **0** new tables / enums / migrations / permission keys / packages / worker jobs / runtime deps; **3** new read-model functions (`querySlaReport`/`queryExceptionReport`/`queryBillingReadinessReport`) + **1** extracted shared helper (`onTimeExpr`, DRY-for-correctness) + the extended `queryAuditLog`; **~4** new BFF endpoints (`GET /api/reports/sla`, `GET /api/reports/exceptions`, `GET /api/reports/billing-readiness`, all `view_all_trips`) + **1** extended endpoint (`GET /api/admin/audit-logs` — actor/date-range filters, `view_audit_log`); **1** new screen (`(shell)/reports/`) + the extended `(shell)/admin/audit/` screen + **1** nav entry (Reports → `view_all_trips`); **2** new Zod query schemas + i18n namespaces; **the hardening pillar** — `permission-coverage.spec.ts` + `audit-completeness.spec.ts` + the extended `messages.test.ts` + a recorded performance validation + the **MVP acceptance traceability matrix** ([contracts/acceptance-and-hardening.md](./contracts/acceptance-and-hardening.md)). **Open items are gated business inputs — provisional defaults + blocked sign-off, not invented** (Constitution II / clarify Q1): per-customer SLA rules (§29 Input #2 → SLA-reporting sign-off blocked), per-customer document/billing rules (§29 Inputs #3/#4/#5 → billing-readiness-reporting sign-off blocked).

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

Confirmed against `.specify/memory/constitution.md` (v1.0.0):

- [x] **Simplicity (I)**: The slice adds **no new table, enum, migration, permission key, package, worker job, or runtime dependency** — it is read-only projection over existing data. The three report functions are concrete read models beside 005's `trips-read.ts` (not a generic "reporting engine"). The single extraction — `onTimeExpr` (the on-time pickup/arrival predicate) — is **DRY-for-correctness mandated by clarify Q4** (the report and dashboard must never diverge on on-time %), consolidating an existing inline computation into one canonical helper used by two concrete call sites; it is the **simplest way to satisfy** FR-006, not a speculative abstraction, so it needs no Complexity-Tracking justification. MVP reports are **tables + summary cards** — **no charting dependency** is introduced (charts are Later). The audit view **extends** an existing endpoint/screen rather than building anew.
- [x] **Scope (II)**: Strictly SLA-005 + REP-002/003/004 + the §21.5 audit-history gap + the §22 Phase 5 hardening bars + the §23 acceptance validation (SPEC-SLICING 009). Lane performance (REP-006), carrier scorecard (REP-007), profitability/revenue dashboards (REP-008, §15.11 revenue lines), advanced BI / data-warehouse / materialized views / ETL, and aggregate-report CSV export (raw extraction stays 005's REP-005) are **out of scope**. Gated inputs are **provisional defaults + blocked sign-off, never invented** (clarify Q1): SLA reporting on `DEFAULT_SLA_POLICY` (§29 Input #2), billing-readiness reporting on the default checklist + manual values (§29 Inputs #3/#4/#5) — each surfaced with a visible provisional banner and a blocked sign-off, **not** an acceptance failure (FR-015).
- [x] **System-of-record (III)**: Reports are **read-only projections**; Postgres remains the source of truth. **Final SLA classification stays server-side** — the report *displays* the stored `trips.sla_status` (007) and never re-classifies in the UI (STACK §6.1). Billing status is the **003 `billingStatus(current_status)` projection** (not re-derived). Audit history (`audit_logs`/`trip_events`) is **append-only**; the audit view only SELECTs — it never mutates or deletes. Soft-deleted/archived records are excluded from operational counts but **retained** and reachable in the audit view (history is never hidden).
- [x] **Authz & secrets (IV)**: Every report read goes through the **BFF** + `requirePermission` — `view_all_trips` for the three reports (mirrors the 005 dashboard), `view_audit_log` for the audit view (Admin, reused from 001); SLA-rule/document-requirement admin stays on `manage_commercial_data` (002). **No new permission key.** Reads are not audited (consistent with the existing model — only mutations are). RLS deferred; service-role key server-only; gateway/PostgREST never exposed. The hardening pillar **verifies** this discipline end-to-end (the permission-coverage + audit-completeness suites).
- [x] **Config over code (V)**: Reports reflect whatever per-customer **SLA rules** (`customer_sla_rules`) and **document/billing config** are in force (or the documented defaults) — **one report engine parameterized by customer/lane/period filters**, never per-customer report code or layouts (per-customer invoice layouts are BILL-009, Later). Customer variation surfaces only as data + i18n labels.
- [x] **Tech constraints**: Freshness is **polling** (TanStack Query `refetchInterval`, reusing the dashboard cadence). Reports compute **synchronously** in the BFF (small aggregates) — **no worker job, no Realtime, no Edge Functions, no Redis/BullMQ, no microservices, no route optimizer**. One app, one worker (unchanged). Postgres/Auth/Storage only.
- [x] **Workflow**: Short-lived `009-reporting-audit-hardening` branch → PR to **`dev`**; CI gates (lint/typecheck/build/tests) must pass — and for this slice the green CI gate **is part of the deliverable** (the §22 Phase 5 / SPEC-SLICING 009 exit criterion "lint, typecheck, tests, and build pass before PR"); PR template used; AI does not merge to `main`.

**Result: PASS.** The slice is read-only over existing data and adds no new durable state, key, package, dependency, worker job, or migration; the one extraction (`onTimeExpr`) is DRY-for-correctness (the simplest way to satisfy "report and dashboard must agree"), not a speculative abstraction; the audit view extends an existing surface; gated inputs are provisional-default + blocked-sign-off. **Complexity Tracking is therefore empty.**
